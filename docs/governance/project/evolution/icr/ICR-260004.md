# ICR-260004: Rename the planned day to a planned workout in the atom shape

## 1. Request Metadata

- Request ID: `ICR-260004`
- Status: `Open`
- Date: `2026-09-29`
- Requester: the repository owner; drafted in session at the owner's request
- Affected contract(s): [`liftrack-atom-shape-contract.md`](../contracts/liftrack-atom-shape-contract.md)
- Priority: `medium` — free today, because no atom of this shape exists; a migration of every
  affected atom once the first one is written (Risks). Decide before EPIC-260001's first write.

Unlike ICR-260001 and ICR-260003, this is not an ask of the Crystord Engine. The contract is
one-party — Liftrack is its only writer and only reader, and the engine sees a free-string label
and opaque list content — so **the repository owner decides it alone**.

## 3. Current Contract

- Contract identifier: `liftrack-atom-shape-contract.md`, status `Proposed`.
- Current behavior: an entry of the plan is a **planned day** — label `LiftPlanDay` beside its plan
  key `LiftP<NNNN>` (§1, §2), rows versioned as `planday/v1` (§3.1, I4, I6), bonded to its plan and
  linked from the sessions performed against it (§4, the chain `perf → session → planDay → plan`),
  shown in worked payload (a) (§7) and counted in the atom budget (§8).
- Current consumers: none in code. The app reads `content/` files (ADR-260008), and the contract's
  status note records that nothing has been written to a server and no atom of this shape exists.

## 4. Proposed Change

- Proposed behavior: `LiftPlanDay` → `LiftPlanWorkout`, `planday/v1` → `planworkout/v1`, and
  "planned day" → "planned workout" throughout the contract's prose — `planDayUuid` →
  `planWorkoutUuid`, the chain `perf → session → planWorkout → plan`, and the example title
  `"Push day A"` → `"Push workout A"`. Row layout, bonds, keys and every other schema id are unchanged.
- Change type: `breaking` in name only — one label and one schema id; no behavior changes.
- Why the current contract is insufficient: the owner's instruction of 2026-09-29, *"workout is the
  right wording"*, and *"please change all the words where day is used to workout instead even the
  non-visible ones"*. The app, `content/plan.json` (ADR-260008, amended 2026-09-29) and the owner's
  notes now say workout; this contract is the last place where a plan entry is a day. Kept, it
  needs a workout ↔ planned-day translation in the backend adapter for good, and "day" keeps two
  meanings — a calendar day and a plan entry — which is what the owner removed.

## 5. Impact Analysis

- Technical impact: the contract's text only. The backend adapter (EPIC-260001) does not exist yet
  and would be written with the new names from the start.
- Consumer impact: none in code. Records that use the contract's vocabulary and would be amended
  with it: [ADR-260001](../adr/ADR-260001.md) (its label list and its plan-as-atoms Decision), and
  REQ-FR-260002 and REQ-FR-260003 ("planned day"). Until then, `project-instructions.md` §1 maps
  the old term to the new one.
- Operational impact: none — no deployment reads or writes the backend.
- Risks:
  - **Deciding after the first write.** ADR-260001 rules out renaming a label once atoms carry it,
    and the engine cannot rewrite labels or opaque content in place: the rename would become a
    client-side rewrite of every `LiftPlanDay` atom and every session bond pointing at one. That
    is the reason to decide before EPIC-260001 writes anything.
  - **A workout beside a session.** A planned workout is what to do; a session is what was done
    on a date (§2). The contract already defines both; the wording must keep them apart — never
    "workout" for a performed session.
  - `LiftPlanWorkout` is 15 characters, well inside the label charset `[A-Za-z_][A-Za-z0-9_]{0,127}`.

## 6. Compatibility Strategy

- Backward compatibility plan: none needed — no atom carries the old label or schema id. Renamed
  in place; `planworkout/v1` starts at `v1` because `planday/v1` was never written.
- Deprecation path: n/a.
- Sunset timeline: n/a.
- If rejected: the contract keeps `LiftPlanDay` and `planday/v1`, gains a one-line note that its
  "planned day" is the app's workout, and the adapter maps one to the other, one for one.
