## 3. Current Contract

- Contract identifier: ADR-260008's Decision, amended last on 2026-10-14 (picture credits).
- Current behavior: four files in `content/` — `exercises.json`, `plan.json`, and the optional
  `exercise-groups.json` and `picture-credits.json` — plus `content/pictures/`. CI rejects any
  field a format does not define. The page shows a workout's name, then its exercises, and
  nothing else.
- Current consumers: the file-backed source (`src/content-source/`), the CI content check
  (`real-content.node.test.ts`) and the end-to-end content reader (`e2e/content.ts`).

## 4. Proposed Change

- Proposed behavior: a fifth, **optional** file, `content/guide.json`. If it's there, every
  workout page shows a **"How to do the sets"** panel between the workout name and the exercises.
  The panel is closed when the page opens, so the exercises stay first, and opens with one tap. The
  file holds a title and a list of sections. Each section has a heading and either a table
  (columns, then rows with one text cell per column) or a list of short lines. The first content,
  taken from the owner's notes (`program-context.md` §5):

  ```json
  { "title": "How to do the sets",
    "sections": [
      { "heading": "The four sets",
        "table": { "columns": ["Set", "Weight", "Reps"],
                   "rows": [["1", "60% of top weight", "10, easy (about 5 if already warm)"],
                            ["2", "90%", "10"],
                            ["3", "95%", "10"],
                            ["4", "100% — top weight", "10, with 1–2 more possible"]] } },
      { "heading": "Set 4 by session",
        "table": { "columns": ["Session", "Set 4"],
                   "rows": [["Upper body", "10 reps, 1–2 more possible"],
                            ["Legs, no Friday match", "10 reps, 1–2 more possible"],
                            ["Legs, Friday match", "Stop at 8, same weights"],
                            ["Full body, no Sunday match", "Legs: about 1 more possible. Presses and rows: 1–2"]] } },
      { "heading": "Good to know",
        "items": ["Top weight: the weight where set 4 lands at about 10 reps, close to failure.",
                  "Set 4 reaches 10 clean reps: next time, raise the top weight by the smallest step. Sets 1–3 follow.",
                  "Round to the nearest weight the machine or dumbbells allow.",
                  "Bodyweight exercises and holds: 4 equal sets. The light 3-set exercises: no build-up, never near failure."] } ] }
  ```

- What CI rejects (the same strictness as the other files): a file that is not an object; a
  missing or empty `title`; no sections; a section with no heading, with both `table` and `items`,
  or with neither; a table with no columns or no rows, or a row whose cell count differs from the
  columns; an empty cell, column or item; any field the format does not define. No file at all is
  valid, and the page then shows no panel, which is today's page.
- Change type: `additive` — a new optional file. The four existing formats, the plan and the
  `WorkoutSource` interface are unchanged: the guide is not workout data, so a small reader of its
  own loads it, bundled at build time like the rest of `content/`.
- Why the current contract is insufficient: the rules for the four sets live only in the owner's
  private notes, which can't be opened in the gym. No current file has a place for text that
  belongs to every workout rather than to one exercise or one workout.

## 5. Impact Analysis

- Technical impact:
  - A validator beside the existing ones, with its negative controls.
  - The guide reader.
  - One panel component above the exercises.
  - The CI content check and the end-to-end content reader read the new file.
  - A README section on writing it.
  - About 1–2 KB more in the bundle.
- Consumer impact: none outside the repository. The owner gains one optional file to edit.
- Operational impact: none. A guide change is a commit and a rebuild, like any content change.
- Risks:
  - **Public text.** The site and the repository are public (ADR-260008, Consequences). The guide
    holds training rules only; the shoulder and every other health detail stay in the private
    notes.
  - **Two copies of the rules.** The guide repeats `program-context.md` §5. The notes will name
    `content/guide.json` as the copy shown in the gym, so a change to the rules updates both.
  - **Small screens.** The tables must fit 360 px at the 16 px text floor. The existing layout
    check covers every workout, and it will run with the panel open.

## 6. Compatibility Strategy

- Backward compatibility plan: additive. An absent file means no panel, and existing content
  passes unchanged.
- Deprecation path: n/a.
- Sunset timeline: n/a. When the backend arrives, the guide stays a static file, like the pictures
  (ADR-260008).
- If rejected: the rules stay in the private notes only.

## 7. Migration Plan

- Step-by-step migration:
  1. The owner approves or rejects this request (§9).
  2. On approval, in one change:
     - amend ADR-260008 (Decision: the fifth file; Verification: its negative controls) with a
       dated note citing this ICR;
     - add a task to [EPIC-260007](../epics/EPIC-260007.md);
     - add the validator, reader, panel and tests;
     - write `content/guide.json` as in §4;
     - add the README section;
     - point `program-context.md` §5 at the file.
  3. Mark this request `Implemented`, naming the commit.
- Validation checkpoints: every negative control fails the content check, while the real
  `content/` passes it; the built page shows the panel closed and opens it to the file's
  sections.
- Rollback plan: delete `content/guide.json` to hide the panel, or revert the commit. Nothing is
  stored anywhere else.

## 8. Verification Plan

- End-to-end behavior checks (built site, phone viewport, served under a sub-path):
  - the panel is visible on every workout and closed by default;
  - opened, it shows each heading, table cell and line of `content/guide.json`, read from the file
    at test time rather than written into the spec;
  - the layout check passes with the panel open.
- Contract/integration tests: the validator's negative controls above, plus a positive fixture;
  a unit check that the panel renders the title closed and the sections when opened; content
  with no guide file renders no panel.
- Observability checks: n/a — a static page.
