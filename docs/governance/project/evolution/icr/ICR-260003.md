# ICR-260003 — Atom timestamps and temporal filtering for session-by-date reads

**Consumer endorsement, not a new proposal.** Engine ICR-260024
(`docs/governance/project/evolution/icr/ICR-260024.md` in the Crystord Engine repository — cited
by path, not linked: that repository is not a build- or review-time dependency of this one)
(`Open`, `pending`, **not approved**) already specifies everything Liftrack needs: nullable
`createdAt`/`updatedAt`, half-open `created`/`updated` ranges, `AtomChangeKind`, a whitelisted
`sort`, client-reachable `limit`/`offset`. This record re-specifies none of that shape. It exists
to register Liftrack as a stakeholder before §9 there is decided, and to state the one caveat
Liftrack needs recorded regardless of the outcome.

## 3. Current Contract

`retrieve` and `AtomOutput`, schema `9.3.0` ([`schema.graphql:9`,
`:249-263`](../../../../backend/schema.graphql)): no temporal argument, no timestamp on an atom.
`WorkspaceOutput`, `CategoryDimensionOutput` and `CategoryValueOutput` all carry
`createdAt`/`updatedAt`; atoms are the sole outlier. Current consumers, enumerated not assumed:
`crystord_app` (three profiles), `crystord_gsheets`, `crystord_probe`, `crystord_engine_harness`
(engine ICR-260024 §3), plus Liftrack — absent from that table because it postdates it. This
record's sole ask under §4 is to add it.

## 4. Proposed Change

Exactly what engine ICR-260024 §4.1 already proposes; Liftrack contributes three things instead of
re-specifying it. **(1) A named consumer:** add Liftrack and its pin (`^9.3.0`, ADR-260004) to that
record's §3 table before §9 is decided. **(2) The acceptance criteria at §8 below**, all already
committed to there. **(3) A caveat:** `createdAt` is record-time, not event-time, and a backfilled
entry breaks that equivalence — Liftrack does not ask the engine to carry a domain event date and
keeps the workout date as its own atom data (ADR-260001) regardless of this ICR's outcome.

## 5. Impact Analysis

None of Liftrack's own — it inherits the change. Liftrack's pin is `^9.3.0` (ADR-260004), so
`9.4.0` does not block it, unlike `crystord_app` and `crystord_gsheets`, recorded in ICR-260024 §3
as hard blocks on a purely additive change because both pin `~9.3.0`. Risk: an epoch-0 coalesce on
a nullable stamp would put every pre-backfill session in 1970 — ICR-260024's own concern, endorsed
here because Liftrack would render that date to a user.

## 6. Compatibility Strategy

Inherited: `9.3.0 → 9.4.0`, additive → MINOR. The one decision Liftrack records for itself: pin
`^9.3.0`, never `~9.3.0` — a static page has no flag to flip, so a blocking gate is an outage
nobody can clear until a human pushes a commit (ADR-260004).

## 7. Migration Plan

Liftrack ships against `9.3.0` with the workout date in its own atom data and a `LiftM<YYYYMM>`
month-bucket label used by one query (ADR-260001, ADR-260006). On `9.4.0`, the month bucket is
replaced by a `created` range and deleted — the designated removable seam, written at create, read
by one path, needing no migration. `LiftD<YYYYMMDD>` stays, being event-time, not record-time.

## 8. Verification Plan

A session written on day D is returned by a `created` range covering D and by none covering only
D−1 or D+1, with a positive control so an always-empty filter cannot pass. An atom with no
creation stamp renders `createdAt: null`, never coalesced to epoch 0. Observability: n/a for
Liftrack — a static client with no server or log sink (ADR-260002, REQ-OR-260002).
