## 4. Proposed Change

- Proposed behavior/signature — two separable asks. **A, publish the cap:** give `retrieve` the
  paragraph `listLabels` has at `:253-256` — default page size, maximum, membership above the cap
  unspecified, no truncation flag. **B, a truncation signal:**
  `retrieveCount(labels, uuid, categories): Int!`, the access-scoped match count over `retrieve`'s
  predicate. **Precedent ships today:** `count(DISTINCT a)` over an access-scoped match is
  published as `CategoryChildCount.atomCount: Int!` (`qt_category.py:328-329`). Rejected: a
  `truncated` flag retypes `[AtomOutput!]` as a connection, breaking/MAJOR.
- Change type: `additive` — ask A is documentation-only, ask B a new root field.
- Why current contract is insufficient: **truncation is unfalsifiable client-side.** A bare list
  makes 25 rows indistinguishable from "25 matched" and from "800 matched" — no flag, count,
  cursor or error — so consumers render partial data as whole. **ICR-260024 does not fix this:**
  reachable `limit`/`offset` only lets a client *infer* "probably more" from a full page,
  ambiguous at the boundary.

## 5. Impact Analysis

- Technical impact: ask A touches one documentation file and the interface bundle; ask B adds a
  resolver, a query template and an SDL field — no plan, index or type change.
- Consumer impact: **none forced** — additive, no response shape changes. Liftrack's broken flow:
  "what did I lift last time" reads `retrieve(labels: ["LiftPerf", "LiftEx0007"])`; if the lift is
  not in the newest 25 matches it shows "no recent data", **indistinguishable from "never
  performed"**; its history view likewise passes off 25 sessions as a training history.
- Operational impact: a count roughly doubles a row-rendering view's read cost, on an unindexed
  scan with no read-path rate limiter (`query_limits.py:12-14`). **Liftrack will call it only on
  history views.**
- Risks: count and page can disagree under a concurrent write — a race
  `CategoryChildCount.atomCount` already carries. Not acting leaves today's state: silent partial
  reads in every consumer, undetectable by any of them.

## 7. Migration Plan

- Step-by-step migration: (1) ship ask A alone; (2) Liftrack records the cap in its contract
  record and stops treating a `retrieve` result as complete; (3) if ask B ships, Liftrack adopts
  it on history views under ADR-260006.
- Validation checkpoints: after (1) the guide's `retrieve` entry states a cap, checkable by
  reading it; after (3) a successful `retrieveCount` probe, an absent field read as "not present".
- Rollback plan: ask A reverts as documentation; removing ask B's field would itself be MAJOR, so
  rollback is Liftrack ceasing to call it — one flag, no data migration.

## 8. Verification Plan

- End-to-end behavior checks: seed 26 atoms under one caller-owned label; assert `retrieve`
  returns 25 and the 26th is unreachable by any client-sendable argument (the red state), then
  `retrieveCount` returns 26 while the page returns 25 — **with a positive control**, a 3-atom
  label returning count 3 and 3 rows.
- Contract/integration tests: access-scoping parity (a share-readable atom counts as `retrieve`
  returns it, an unreadable one in neither) and argument parity — both fields taking the same
  filters and agreeing under the cap.
- Observability checks: n/a for Liftrack — a static client with no server or log sink (ADR-260002,
  REQ-OR-260002); engine-side cost is the engine's to watch, per §5.
