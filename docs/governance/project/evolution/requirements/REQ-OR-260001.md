# Requirement: REQ-OR-260001 `Static hosting on GitHub Pages`

Single requirement record. The ID encodes the class: `REQ-FR-…` (functional behavior),
`REQ-QR-…` (quality attribute), `REQ-OR-…` (operational), `REQ-CR-…` (constraint/compliance).
Status values: see `docs/governance/generic/process/artifact-model.md`.

- Requirement ID: `REQ-OR-260001`
- Title: `Static hosting on GitHub Pages`
- Class: `OR`
- Status: `Proposed`
- Owner: `Repository owner`

## Statement

The system shall be deliverable as static files served by GitHub Pages, with no server runtime
of its own, all environment-specific configuration resolved at build time, every asset resolving
under the configured base path, and every in-app route reachable by a cold deep link.

## Rationale

The owner's stated hosting constraint is "as long as it can be used in github pages". Pages
serves bytes only: there is no request-time code, no API route, no proxy, no rewrite rule and no
response-header control. That removes a whole class of designs rather than degrading them, so it
has to be a stated, checkable constraint and not an assumption discovered on deploy day. The
Crystord Engine is then Liftrack's only network dependency besides its own origin.

## Acceptance Criteria (behavioral)

- The published artifact contains static files only. The running app makes no request to any
  origin other than its own and the configured backend (plus the Google identity origin if
  Google sign-in ships), verified by a network trace over a full plan-and-log session.
- Every environment-specific value — backend GraphQL endpoint, pinned schema range, build
  identifier — is produced by the build from a named profile and is present in the published
  artifact; the app reads no runtime environment variable, and the same commit built for a
  different profile differs only in generated configuration, never in source.
- A deploy to the chosen hosting target loads with zero 404s and zero MIME-type errors on first
  paint, verified by an automated fetch of the deployed URL. The base path is a build input, and
  the check fails if any asset URL resolves outside it (the failure this guards is a project
  site at `/<repo>/` built with a root base, which serves the 404 page in place of the bundle).
- A cold deep link to any in-app route, opened in a fresh browser session, renders that route
  rather than the app root or a 404 page; reloading on that route keeps it. The routing
  mechanism that achieves this is [ADR-260002](../adr/ADR-260002.md)'s decision.
- The deploy pipeline fails rather than publishes when the generated configuration is missing
  the endpoint, the schema range or the build identifier, so a half-configured artifact cannot
  reach the Pages site.
