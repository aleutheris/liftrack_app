## Statement

The system shall persist every authored plan and every recorded set to Crystord Engine so that both
read back unchanged after the app is closed and reopened, and — holding no store of its own — shall
surface every failed write as a failure, keep the entered values on screen and retryable, and never
present unsaved data as saved.

## Rationale

The owner's framing is that this "is a web project, which connects to an already existing backend
system". Liftrack therefore owns no storage: ADR-260002 makes it a static page with no server runtime,
ADR-260003 makes the MVP online-only with no offline store and no write queue, and records single
device, single tab as a working assumption rather than a commitment — this requirement does not
promise cross-device read-back, and does not contradict that assumption by accident. The consequence
of owning no storage is sharp regardless of device count — a failed mutation has nowhere to go, and
the set exists only in the browser tab that typed it. An optimistic tick, a silent retry, or a
navigation that clears the form each turn a recoverable network error into training data the user
cannot recover and cannot even know is gone. Failure is ordinary here, not exceptional: the session
can expire between typing a weight and saving it (REQ-FR-260001), and an update replaces every field
it carries while leaving unchanged every field it omits, with no merge
([`backend-user-guide.md:931-932`](../../../../backend/backend-user-guide.md)) — so a half-populated
write is silent data loss, not a visible error.

## Acceptance Criteria (behavioral)

- End-to-end: a workout logged in one session reads back with identical sets, reps, weights and unit
  after a cold reload of the app.
- End-to-end: closing the tab mid-workout and reopening the app returns every set already saved, in
  order, with no loss and no duplication.
- End-to-end: with the backend unreachable, saving a set surfaces an explicit failure and keeps the
  entered reps and weight on screen; once connectivity returns, a retry saves that set exactly once.
- End-to-end: a set shows as recorded only after `change` returns the affected atom UUID
  ([`schema.graphql:117`](../../../../backend/schema.graphql)); an errored write leaves it unsaved.
- End-to-end: a GraphQL error is surfaced with the backend error code visible to the user rather than
  collapsed into a generic message, so an unanticipated failure is reportable.
- Contract check: after an edit the atom reads back with its labels and every untouched field intact.
