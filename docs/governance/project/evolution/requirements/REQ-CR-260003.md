# Requirement: REQ-CR-260003 `No silent truncation of a bounded result set`

Single requirement record. The ID encodes the class: `REQ-FR-…` (functional behavior),

Status values: see `docs/governance/generic/process/artifact-model.md`.

- Requirement ID: `REQ-CR-260003`
- Title: `No silent truncation of a bounded result set`
- Class: `CR`
- Status: `Proposed`
- Owner: `Repository owner`

## Statement

The system shall never present a backend result set as complete when the backend may have
truncated it.

## Rationale

`retrieve` silently caps its result at 25 atoms and a client can neither raise nor detect that:
`_DEFAULT_RETRIEVE_LIMIT = 25` / `_MAX_RETRIEVE_LIMIT = 100`
(`crystord/atom_interactions/inter_fundamentals.py:1406-1407`) are applied at `:1419`, and
`crystord_server/resolvers.py:86-91` never forwards a limit. The published `retrieve`
(`schema.graphql:9`) offers no `limit`, `offset`, sort or count, its response is a bare
`[AtomOutput!]` with no flag or cursor, and the backend user guide documents the cap for
`listLabels` but never for `retrieve`. Truncation therefore reaches the client as data that is
simply absent — a correctness failure, since a truncated workout looks like a complete one.

## Acceptance Criteria (behavioral)

- Every read path is recorded in [ADR-260001](../adr/ADR-260001.md) with its expected maximum
  result size, and each gym-time read is bounded below the cap by construction — verified by
  seeding a worst-case day (7 exercises × 5 sets) and asserting each returns fewer rows.
- Where that bound is not guaranteed — history and browsing reads — a result whose length equals
  the cap is treated as possibly truncated: presented as partial, naming the constraint.
- No aggregate over a possibly-truncated result is presented as authoritative: a total, a
  personal record or a "last performed" answer is withheld or bounded by what was readable.
- A session whose atoms come back at the cap renders the truncation state instead of its sets; a
  partially-retrieved workout is never displayed as a whole one.
- The cap is a single named constant derived from the schema version the handshake reports, so
  it moves when the contract moves (25 today; 100 stays the maximum even if engine ICR-260024
  lands — it is `pending` there and explicitly not a page-limit amendment).
- Nothing in Liftrack infers completeness from the absence of an error: a successful `retrieve`
  is never evidence that its result is complete.
