# Requirement: REQ-CR-260001 `Consume the Crystord contract unmodified`

Single requirement record. The ID encodes the class: `REQ-FR-…` (functional behavior),
`REQ-QR-…` (quality attribute), `REQ-OR-…` (operational), `REQ-CR-…` (constraint/compliance).
Status values: see `docs/governance/generic/process/artifact-model.md`.

- Requirement ID: `REQ-CR-260001`
- Title: `Consume the Crystord contract unmodified`
- Class: `CR`
- Status: `Proposed`
- Owner: `Repository owner`

## Statement

The system shall consume the Crystord Engine GraphQL contract exactly as published by the engine
deployment it connects to, and shall obtain any change it needs to that contract through an
Interface Change Request raised with the Crystord Engine project — the workflow in
[`framework.md`](../../../generic/process/framework.md) §3 — never by unilateral adaptation.

## Rationale

Liftrack is a consumer with no authority over the engine interface and no write access to the
engine repository, and the engine is a moving target with work in flight that would change
`retrieve`. Both halves need constraining: Liftrack must not reach around the published contract
to get what it wants, and must not record engine work as available before it is approved there.

## Acceptance Criteria (behavioral)

- Every operation, argument and field selection Liftrack issues exists in the schema the target
  deployment reports, verified by a contract check that validates Liftrack's documents against
  that schema; an unknown field fails the check rather than failing at runtime.
- Liftrack depends on no engine behaviour the published SDL does not expose. Named exclusions,
  each real in the engine and unreachable from `retrieve`: the internal `offset`
  (`crystord/atom_interactions/inter_fundamentals.py:1424`, commented "Internal offset support
  (no GraphQL `retrieve` arg)"), a `limit` the resolver never forwards
  (`crystord_server/resolvers.py:86-91`), and `Selector.uuids`, on the destroy path only.
- Every capability Liftrack needs and the contract does not provide is recorded as an ICR in
  Liftrack's own register, ready to be put to the Crystord Engine project — two stand drafted
  and not yet submitted: [ICR-260001](../icr/ICR-260001.md), [ICR-260003](../icr/ICR-260003.md).
  Recording a need is not the same act as raising it, and no record in this project claims the
  second has happened.
- No Liftrack record or behaviour treats engine work as available before the engine approves it.
  Engine ICR-260024 — reachable `limit`/`offset`, atom timestamps, temporal filters — is
  `pending` there as of 2026-09-12 and is cited as proposed, never as a capability Liftrack has.
- Liftrack makes no change inside the Crystord Engine repository. The vendored copies under
  `docs/backend/` are evidence; authority is the deployment's `schemaInfo`, read at startup by
  [ADR-260004](../adr/ADR-260004.md)'s handshake.
