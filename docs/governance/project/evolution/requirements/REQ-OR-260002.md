- Requirement ID: `REQ-OR-260002`
- Title: `Client observability minimum`
- Class: `OR`
- Status: `Proposed`
- Owner: `Repository owner`

## Statement

The system shall make four failure classes — authentication failure, backend schema
incompatibility, an incomplete write, and a possibly-truncated read — separately identifiable
from the running client alone, each with a stable code, alongside a build identifier naming the
exact running build.

## Rationale

Liftrack has no server of its own: GitHub Pages provides no access logs, schema 9.3.0 exposes
no telemetry operation, and the app runs on a phone where the browser console is unreachable.
The only guaranteed reader of a diagnostic is the user standing in the gym, so the user-visible
surface is the primary observability mechanism, not a fallback. A report is actionable only if
it identifies the build, the backend it was talking to, and which failure occurred.

## Acceptance Criteria (behavioral)

- Every build embeds a build identifier (commit SHA plus build timestamp). Where and how it is
  surfaced to the user is a UI decision left to the epic that ships each failure state, not
  prescribed here.
- Each of the four failure classes renders a distinct user-visible state carrying its own stable
  short code, distinguishable from one another and from a generic network error. Verified by
  forcing each condition against a stubbed backend and asserting four different codes.
- "Backend unreachable", "backend schema outside the pinned range" and "backend schema version
  unparseable" are three separate states with three different recommended actions, never
  collapsed into one screen — the user's next step differs in each case.
- Whatever surfaces a failure state also shows the build identifier, the configured backend
  origin and the `schemaVersion` reported at startup alongside it, so one screenshot of the
  failure carries everything needed to trace a report unaided — without mandating a dedicated
  screen for this alone.
- No credential, session token or workout content appears in any diagnostic output (REQ-CR-260002).
- Third-party telemetry is an explicit MVP non-goal: the build ships no analytics or
  error-collector SDK, and no workout data reaches any origin but the configured backend —
  verified by REQ-OR-260001's network trace and the page's `connect-src` allowlist.
