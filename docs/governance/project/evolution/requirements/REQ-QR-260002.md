## Statement

The system shall render today's workout and acknowledge a logged set within stated time budgets
on a 1.6 Mbps / 150 ms-RTT mobile connection, and shall never display a set as saved while its
write is in flight or after it has failed.

## Rationale

Gym wifi and cellular indoors are slow and lossy, and the app is online-only (ADR-260003): with
no local store and no write queue, a write that does not complete is data the user does not
have. The profile is 1.6 Mbps / 150 ms RTT ("Slow 4G") — a budget stated against a fast
connection proves nothing about where the app is used.

## Acceptance Criteria (behavioral)

- Cold open to today's workout fully rendered — plan, prescribed exercises and any sets already
  logged today — completes within 4.0 s at the reference profile, from navigation start with an
  empty cache. (Derivation: a config fetch, a `schemaInfo` handshake and the day's reads — 5
  round trips in the shape ADR-260001 proposes, ≈ 0.8 s — plus an initial payload the build
  holds at or below 250 KB compressed, ≈ 1.3 s of transfer.)
- Warm re-render of today's workout, plan and catalogue already in memory: within 1.5 s.
- A touch that logs a set produces a visible state change within 100 ms, before any network
  result, and the set resolves to saved or failed within 2.0 s at the median of a 20-log run.
  (100 ms is the threshold below which a response reads as instantaneous.)
- A set whose write is in flight renders in a "saving" state visually distinct from "saved" and
  is never styled as saved until the mutation returns; a write unresolved after 10 s is
  presented as failed with an explicit retry, not left indefinitely pending.
- A failed write keeps the entered reps and weight on screen and offers retry; no entered value
  is discarded on failure, and no failure is reported only to the console (REQ-OR-260002).
- The logging controls stay interactive while a write is in flight, and writes targeting the
  same atom are serialized, so a later set cannot be overwritten by an earlier write completing
  late. (Forced by the whole-content replace semantics of `change` — ADR-260001.)
