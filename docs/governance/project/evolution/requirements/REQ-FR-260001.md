## Statement

The system shall let a user sign in to their Crystord account, keep that session usable across app
reloads for as long as the backend honours it, and — when the backend rejects a request because the
session has expired or been revoked — prompt re-authentication and return the user to the screen they
were on with any set values entered but not yet saved still present and still saveable.

## Rationale

The owner's usage pattern is one gym visit: open the app, lift for 45–90 minutes, log between sets —
a long-idle pattern against a backend that issues an **expiring, revocable session bearer token**:
idle timeout ~24h, absolute cap ~30 days, revoked by `logout`, `revokeAllSessions`, password reset or
email change ([`backend-user-guide.md:169-172`](../../../../backend/backend-user-guide.md)). No expiry
timestamp comes back with the token and there is no refresh call, so a client cannot predict expiry —
only discover it on the next request. Because the MVP is online-only with no write queue (ADR-260003),
a re-authentication that discards the form loses the set the user just performed, standing at the
rack. Mid-workout re-auth is a normal path here, and preserving entered-but-unsaved input across it is
part of "sign in". REQ-FR-260005 governs failed writes generally; this one, the session's own failure.

## Acceptance Criteria (behavioral)

- End-to-end: signing in with valid credentials reaches today's workout; reloading the app returns to
  the same signed-in state, with no credentials re-entered, while the session remains valid.
- End-to-end: entering reps and weight for a set and then attempting to save against an expired or
  revoked session presents a re-authentication prompt; after a successful sign-in the same reps and
  weight are still on screen and one save action persists them. No entered set is discarded.
- Contract check: a response carrying `AUTHZ-AUTHENTICATION-REQUIRED` **only** inside
  `errors[].message` — the form this contract actually emits
  ([`backend-user-guide.md:180-185`](../../../../backend/backend-user-guide.md)) — triggers
  re-authentication, as does an HTTP 401; neither surfaces as a generic error.
- End-to-end: signing out clears the stored token; the next app load shows sign-in and issues no
  authenticated request.
- End-to-end: sign-in attempts rejected with `AUTH-RATE-LIMITED` produce a distinct "try again later"
  message, never a "wrong password" message, and the app does not retry automatically.
