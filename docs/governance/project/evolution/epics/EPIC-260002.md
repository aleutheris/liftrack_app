# EPIC-260002: Project scaffold and GitHub Pages delivery

> **Parked 2026-09-21** by the owner; status unchanged (`Ideation`). [EPIC-260007](EPIC-260007.md)
> builds the scaffold and a reduced Pages pipeline — lint, type check, tests, build, deploy — on the
> stack of [ADR-260007](../adr/ADR-260007.md), with no backend, and uses a relative base path so the
> hosting target can stay open. Everything backend-facing stays here: the generated configuration,
> the `https://` endpoint gate, the schema-range check, the failure-state taxonomy and the
> hosting-target decision. **Resumes** with the first backend call — and the hosting-target bullet
> must be answered before sign-in, whichever epic resumes first.

- Epic ID: EPIC-260002
- Title: Project scaffold and GitHub Pages delivery
- Persona/Actor: The repository owner as operator — the person who deploys Liftrack and is the only
  person who will notice when a deploy is broken.
- Value statement: For the owner, deliver a repeatable static build and deploy on GitHub Pages, so
  that shipping a change is a push rather than an investigation.
- Context: Liftrack is a purely static single-page client with no server runtime of its own
  (ADR-260002) and no offline store (ADR-260003). Pages serves bytes only: no request-time code, no
  environment variables, no response headers, no rewrite rules and no access logs. Every
  configuration value is baked at build time, and every platform failure is silent.
- Problem statement: Nothing exists — no scaffold, no build, no deploy path — and this platform's
  failure modes are all off-device. A wrong base path serves the 404 page where the JS bundle should
  be; a deployed `http://` endpoint is mixed-content blocked with no user override; a cached
  `index.html` names hashed assets the last deploy deleted.
- Expected outcome: a scaffold that builds and deploys to a known URL, with the build identifier
  visible inside the app and a deploy that refuses to publish a non-HTTPS backend endpoint.
- Success metric(s): a fresh clone builds and deploys with no manual step; a deep link and a reload
  both resolve on the deployed site; CI asserts the built endpoint starts with `https://` rather
  than screening for known-bad hosts; the running build identifier is readable from the UI.
- Non-goals: any server-side component; a service worker or offline caching (ADR-260003);
  third-party telemetry (REQ-OR-260002); SEO and link previews; a second deployment environment
  beyond what the owner actually uses.
- Constraints: static files only and world-readable, so no credential of any kind may reach the repo
  or the build output (REQ-CR-260002); no `Cache-Control`, no CSP header and no `X-Frame-Options` —
  only a `<meta>` CSP is reachable; a deploy replaces the whole site, deleting the previous build's
  hashed assets.
- Dependencies: the owner's answer on the hosting target, which also fixes the Google authorized
  origin in EPIC-260003 and bounds the token store in ADR-260005; the backend staying reachable
  cross-origin (`crystord_server/graphql_app.py:160-165` allows `*` with no credentials today).
- Risks/assumptions: assumes the production endpoint serves a valid public certificate — unverified
  from a checkout; assumes the backend's wildcard origin stays, and a tightening would land as a
  total outage with a console-only error; assumes Pages' cache lifetime on `index.html` is short,
  which was not measured.
- Target window: TBD.
- Validation approach: an end-to-end check against the deployed URL — load, deep-link, reload, and a
  first GraphQL call that returns; a CI assertion on the built endpoint's scheme; a deploy-time
  check that the pinned schema range admits the version the live `schemaInfo` reports.

## Ideation Bullets

- [ ] **Hosting target: project site, user site, or custom domain?** They differ in base path and,
  decisively, in origin: `https://<owner>.github.io/liftrack/` shares one origin with every other
  Pages project on the account, so any of them can read Liftrack's stored session token. The same
  answer fixes the Google authorized origin and how defensible `localStorage` is.
- [ ] **Routing: hash URLs, or the `404.html` rewrite trick?** Hash routing always returns 200 and
  survives a hosting move, at the cost of clean URLs and the fragment. The 404 trick buys clean URLs
  and pays with a genuine HTTP 404 on first response, a redirect flash, nothing without JS, and a
  path-depth constant that must track the base path or loop.
- [ ] **Build-time configuration: inline the endpoint into the bundle, or fetch a generated file at
  boot?** A fetched file can be repointed without a rebuild and fails legibly; it is also cached
  independently of the bundle, so a fresh build can read a stale endpoint or a stale pinned range.
- [ ] **Confirm the backend's cross-origin posture with its owner, and decide the response if it
  tightens.** Today's wildcard is a current behaviour, not a contract term; turning Liftrack's exact
  origin into a declared input is an ask, and whether to file it belongs to EPIC-260006.
- [ ] **Single bundle, or code-split routes?** Splitting breaks a running session mid-use when a
  deploy deletes the chunk it is about to import; one bundle costs load time and removes the failure
  class outright. If splitting wins, a one-shot reload-and-retry is mandatory, never unconditional.
- [ ] **What does the app show when it cannot reach or cannot accept the backend?** With no access
  logs and a phone-only user, the error surface is the whole observability channel: it must carry
  the schema version, the endpoint host and the build identifier, and must not present "you are
  offline", "the server is down" and "this build is too old" as one screen. **Do not resolve this
  in isolation** — EPIC-260003 and EPIC-260005 each independently enumerate an overlapping-but-
  different failure-state list for the same underlying REQ-OR-260002 requirement; reconcile the
  three into one stable-coded taxonomy here or explicitly hand ownership to one of the other two,
  rather than letting three epics each ship their own.
- [ ] **CI gates: what actually gets built, and by which task?** `project-instructions.md` §5 names
  this epic as the one that builds lint, strict type checking, the unit/component suite and the
  boundary checks from §4 — none of that is currently reflected in this epic's own scope above,
  which has so far covered only the deploy-time endpoint/schema-range guards. Add it explicitly
  here (as its own task once this epic reaches Ready) rather than leaving it as an unclaimed
  cross-reference from a tier-2 document.
