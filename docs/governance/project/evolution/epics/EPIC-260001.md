> **Parked 2026-09-21** by the owner; status unchanged (`Ideation`). Liftrack starts with a static
> page fed from files in the repository ([EPIC-260007](EPIC-260007.md)); sign-in and the backend
> come later. The decision at this epic's core already stands — [ADR-260001](../adr/ADR-260001.md)
> is `Accepted` — and the first slice's content mirrors it ([ADR-260008](../adr/ADR-260008.md)).
> **Resumes** when Liftrack starts reading from the backend, with one new item: the first slice's
> reps-per-side qualifier has no column in `liftrack-atom-shape-contract.md`'s `planday/v1`, so it
> needs a `planday/v2`.

- Epic ID: EPIC-260001
- Title: Agree the workout domain model and backend contract
- Persona/Actor: The repository owner, who must accept a data shape before any Liftrack code is
  written against it.
- Value statement: For the owner, settle how planned and performed workouts are stored as Crystord
  atoms, so that every later epic builds on one agreed shape instead of rediscovering it.
- Context: Liftrack has no code and no data. Crystord Engine 9.3.0 is the only persistence, and
  `retrieve` returns at most 25 atoms with no signal that it truncated
  (`crystord/atom_interactions/inter_fundamentals.py:1406-1407`, applied at `:1419`;
  `crystord_server/resolvers.py:86-91` forwards no limit). The storage grain therefore decides
  whether a single workout is readable at all.
- Problem statement: ADR-260001 and both contracts are Proposed and nothing is agreed. Choosing the
  grain wrongly is not a refactor — `change` batches creates but updates one atom per call, so a
  later regrain is a read-25-at-a-time-and-rewrite migration with no transaction across it.
- Expected outcome: ADR-260001 accepted, amended or rejected by the owner; both contracts ratified;
  any Liftrack payload checkable against a written shape.
- Success metric(s): ADR-260001 leaves Proposed with a recorded owner decision; both contracts reach
  Active; one example payload per record kind validates against `schema.graphql` and the list cell
  rules; the agreed grain keeps one typical session's read strictly under 25 atoms.
- Non-goals: any client code or scaffold; `operation`, computed content, `COLLECT`, workspaces or
  sharing; data migration (there is none); asking the backend for new capability — EPIC-260006.
- Constraints: governance only; schema 9.3.0 consumed unmodified; `content` takes a string, number,
  JSON array or null, never a bare object (`docs/backend/backend-user-guide.md:424`); nothing looks
  inside list content (`:1197-1202`); a bare UUID cell is rejected at any nesting (`:1175-1179`).
- Dependencies: the owner's decision on ADR-260001; a live `schemaInfo` probe confirming the
  vendored `docs/backend/` copy matches the running deployment; EPIC-260006 for the gaps the model
  cannot close inside 9.3.0.
- Risks/assumptions: assumes roughly 3 sessions a week of 5-7 exercises and 3-5 sets, which the
  owner must confirm because the cap argument rests on it; assumes `declaredType: "list"` with
  `typeMode: "flexible"` behaves as backend ADR-260034/260037/260040 describe, which the vendored
  guide does not define; assumes `change` returns created uuids in input order — unverified.
- Target window: TBD.
- Validation approach: contract checks against a live 9.3.0 deployment, each paired with a positive
  control — round-trip one atom of each kind; assert a bare UUID cell fails `AU-TYPE-MISMATCH` on
  create and `AU-TYPE-CONFLICT` on update; assert 26 atoms under one label return 25 unmarked.

## Ideation Bullets

- [ ] **Storage grain: one atom per set, per performed exercise, or per session?** Per-set is 16-36
  atoms for one workout against a 25 cap that drops the *oldest* rows first
  (`crystord/neo4j_query_templates/qt_fundamentals.py:708-709`), so a heavy workout opens at set 12.
  Per-session is one atom but turns "what did I bench last time" into a client-side scan of the
  newest 25 sessions that cannot tell "not in the last 25" from "never". The owner chooses.
- [ ] **Sets as typed list content, or as separate atoms?** If a list, the positional row contract
  and its version tag are fixed here: the server can neither validate nor migrate it, and adding a
  column later rewrites every historical atom one call at a time.
- [ ] **Where does the workout date live?** Atoms carry no timestamps at all — `WorkspaceOutput` and
  both category outputs do, atoms are the sole outlier (`schema.graphql:249-263`) — so the date is
  Liftrack's own data. A label, a constants key, `datetime` content or a category value each cost
  differently on read, and the label charset forbids `-` and `:`.
- [ ] **Categories, labels or bonds for each key — type, date, which exercise, which plan?**
  Categories are the only paginated read path today (`crystord_server/resolvers.py:237-246`, max 100
  at `crystord/atom_interactions/inter_category.py:59-60`) but a referenced value is undeletable;
  labels are free and AND-combinable but each mints schema objects; and no query traverses a bond.
- [ ] **How is order represented** — exercise order within a session, set order within an exercise?
  Array position is free and invisible to the server; an explicit index column survives a reorder
  but widens a row contract that cannot be migrated later.
- [ ] **What happens to history at session 26, and does the model ratify before a live probe?**
  Either accept a truncated browsing screen, add a month-bucket key, or roll months into one atom —
  naming which is the thin removable seam once page bounds become client-reachable. And
  `docs/backend/README.md` calls the vendored contract evidence, not authority.
