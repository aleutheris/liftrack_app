# EPIC-260003: Account access

> **Parked 2026-09-21** by the owner; status unchanged (`Ideation`). The first slice
> ([EPIC-260007](EPIC-260007.md)) has no sign-in, and its content is public on Pages by
> construction. **Resumes** when the owner wants sign-in; EPIC-260002's hosting-target question must
> be answered first, because it decides which sites share Liftrack's browser origin (ADR-260005).

- Epic ID: EPIC-260003
- Title: Account access
- Persona/Actor: The owner as the single Liftrack user, signing in on a phone, often after the app
  has sat idle for days.
- Value statement: For the user, deliver a sign-in that survives a 45-minute workout and fails
  visibly rather than silently dropping a logged set.
- Context: Crystord issues an expiring, revocable session bearer token. `signin` and `signinGoogle`
  return a bare string, there is no refresh call and no expiry timestamp (`schema.graphql:10-11`),
  and the documented lifetimes are approximate — idle around 24h, absolute around 30 days
  (`docs/backend/backend-user-guide.md:169-171`). A client cannot compute expiry; it only discovers
  it on a request that fails.
- Problem statement: Liftrack is a static client with nowhere to put a secret and no queue behind a
  failed write (ADR-260003). A session that ends between typing a weight and saving it loses the
  entry, and the failure arrives as a code inside the GraphQL error `message`, not in `extensions`,
  so a detector that only inspects `extensions` misses it entirely.
- Expected outcome: the user signs in, stays signed in across a reload, and any re-authentication
  mid-workout is non-destructive to what is already on screen.
- Success metric(s): a reload during a workout does not require retyping a password; a forced token
  expiry produces a re-authentication state rather than a generic error; no set is reported saved
  unless its mutation returned; signing out clears the stored token.
- Non-goals: Liftrack's own account or identity system; multi-user, coach or shared accounts;
  workspaces and sharing; password-strength coaching beyond the backend's published rules.
- Constraints: no server-side secret and no `HttpOnly` cookie is available (ADR-260002); the backend
  verifies Google ID tokens against one server-side client ID (`crystord_server/services.py:114-116`
  and `:347-356`, `crystord_server/config.py:43`), so Liftrack cannot mint its own OAuth client;
  unless a custom domain is used, the origin is shared with every other Pages project on the account.
- Dependencies: the hosting target decided in EPIC-260002, which bounds the token store ADR-260005
  proposes; for Google sign-in, an owner action adding Liftrack's origin to a client the backend
  already owns.
- Risks/assumptions: assumes the engine keeps carrying auth codes in the error message string;
  assumes the documented revocation triggers are complete — notably that `setPassword` does not
  revoke while a confirmed password reset revokes even the initiating session; assumes one device
  and one tab.
- Target window: TBD.
- Validation approach: end-to-end sign-in, reload, forced-expiry and sign-out flows against a live
  deployment; an assertion that an expired token yields the re-authentication state and never a
  success indication for a set whose write did not land.

## Ideation Bullets

- [ ] **Which sign-in methods ship in the MVP?** Email and password works with no prerequisite.
  Google requires Liftrack's origin to be added to a client ID owned by the backend, in a Google
  Cloud project Liftrack does not control — a deploy-day blocker if discovered late — and an
  unfamiliar Google address silently creates a second, empty account instead of erroring.
- [ ] **Does signup happen in Liftrack at all?** A full signup means the code-confirmation flow plus
  username and password pre-validation, built for one user who already has an account. Sign-in only
  is far less surface; the cost is that a fresh device cannot bootstrap without another client.
- [ ] **Where is the token stored — memory, `sessionStorage`, or `localStorage`?** Memory forces a
  re-login on every reload and deep link; `localStorage` leaves a token valid for up to 30 days
  readable by every other project sharing a `github.io` origin. The defensible answer depends on
  EPIC-260002's hosting decision and on how much re-authentication the owner tolerates between sets.
- [ ] **What does re-authentication look like mid-workout?** The session can end on any request and
  nothing queues behind it. Does the app block on a modal, or keep the in-memory form and
  re-authenticate in place — and what is shown for a set whose write never landed?
- [ ] **Which account operations does Liftrack expose at all** — sign out, revoke all sessions,
  password reset, email change, account deletion? Revoking all sessions is the only compromise
  recovery a static client has; account deletion is refused while the user still owns atoms, making
  it a delete-everything-first loop driven by a capped read.
- [ ] **How are "you are offline", "the backend is unreachable", "your session expired" and "this
  build is too old" told apart?** Online-only operation makes this the most-seen surface in the
  product, and each of the four demands a different action from the user. **This is the same
  underlying question EPIC-260002 and EPIC-260005 each raise independently** for their own corners
  of it (deploy/schema-version failures; write/read failures) — REQ-OR-260002 needs one coherent,
  stably-coded taxonomy across all of them, not three separately invented lists. Given this bullet
  is the most complete of the three, resolve it here first and have the other two epics reference
  this taxonomy rather than each defining their own.
