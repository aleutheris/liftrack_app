> **Parked 2026-09-21** by the owner; status unchanged (`Ideation`). [EPIC-260007](EPIC-260007.md)

> logging stays here. Two inputs changed while it is parked: the owner now wants **two pictures per
> exercise**, which overtakes this epic's "exercise media" non-goal; and "what does today mean" is
> set aside for the first slice — the owner pages to the day — and returns here with logging.
> **Resumes** with set logging.

- Epic ID: EPIC-260005
- Title: Today's workout and set logging
- Persona/Actor: The owner mid-workout — one hand free, a phone, rest running out, gym wifi.
- Value statement: For the user at the gym, show what to do today and capture every set's reps and
  weight as it is completed, with no doubt about whether it saved.
- Context: This is the product's reason to exist and its only latency-sensitive screen. It is also
  where the backend's sharpest edges meet the user: a read that caps silently, a session token that
  can expire at any request, and no queue behind a failed write (ADR-260003).
- Problem statement: None of the questions that decide this screen are answered — what today means,
  what happens when the user deviates from the plan, what a weight's unit is, and what the user sees
  when a write fails while they are standing at the rack.
- Expected outcome: the user opens Liftrack at the gym, sees the day's exercises with their planned
  sets and reps, logs each set's reps and weight as it happens, and finishes with an unambiguous
  record of what was actually performed.
- Success metric(s): a complete workout is logged without leaving the screen; the day's read returns
  the whole session and stays well under 25 atoms; no set is ever presented as saved before its
  mutation returned; a deviation from the plan is recordable without abandoning the plan.
- Non-goals: rest timers, plate maths, personal-record detection, charts and analytics; exercise
  media; anything social; offline logging or a write queue (ADR-260003).
- Constraints: the atom shape from ADR-260001; writes are uncapped but reads are not; there is no
  partial or append mutation, so every logged set rewrites its atom's content whole and each write
  adds a change event; one-handed mobile use (REQ-QR-260001) on a slow network (REQ-QR-260002).
- Dependencies: the durable records EPIC-260001 spawns — ADR-260001 accepted and both contracts
  Active — rather than that epic's own completion. It is the ratified atom shape, not the planning
  work, that gates this design.
- Risks/assumptions: assumes one device and one writer, which is what makes whole-atom rewrites
  safe; assumes the user logs during the session rather than reconstructing it afterwards, which
  decides whether the live-write path or the backfill path is primary; assumes gym connectivity is
  usable at all, which online-only operation makes a hard requirement rather than a preference.
- Target window: TBD.
- Validation approach: an end-to-end logged workout against a live deployment, including one
  deviation and one forced write failure; an assertion that the day's read never returns exactly the
  cap; a check that what was saved matches what the screen displayed.

## Ideation Bullets

- [ ] **What does "today" mean?** On a calendar plan it is the weekday; on a rotation it is the next
  unperformed day, which must be derived from history that the 25-atom read bounds. And what does
  the screen show on a rest day, or when the user is two sessions behind the schedule?
- [ ] **Are unplanned sessions supported?** Walking in and logging something on no plan at all is
  ordinary behaviour. Supporting it means a session record that references no planned day, which
  changes the shape ADR-260001 ratifies rather than only the screen.
- [ ] **How is deviation recorded** — an extra set, fewer sets than planned, a swapped exercise, a
  skipped exercise, a reordered session? Either the log records only what happened, or it records
  the actual against the prescription. The second is what makes the plan worth having, and it widens
  the row contract that cannot be migrated later.
- [ ] **Units: kg or lb, and fixed at which level** — account, plan, exercise, or logged set?
  Storing an entered number and storing a converted number are different records, and mixing the two
  is unrecoverable once history exists; the answer also decides whether a set row stays all-numeric.
- [ ] **When is a write issued — per set, per exercise, or at the end of the session?** Per set
  gives the smallest loss window and the most change events on one atom; batching to the end is one
  clean write that loses the entire workout if the session expired somewhere inside it.
- [ ] **What does the user see after the last set?** An explicit finish that writes something, or
  implicit completion that writes nothing more — and whether finishing shows a summary, the next
  planned day, or simply returns to where the user started.
- [ ] **What must the UI never claim?** With nothing queued behind a failed mutation, a set that did
  not save must never look saved. The open question is what it looks like instead, and whether the
  user can retry without retyping the numbers they just entered.
- [ ] **What does this screen show when its own read comes back at the 25-atom cap?** REQ-CR-260003
  requires the possibly-truncated state to render instead of the sets — this is the epic that owns
  building it, since EPIC-260001 and EPIC-260006 only establish why it is needed. Given today's
  atom-count budget (`liftrack-atom-shape-contract.md` §8) this screen's own reads never actually
  reach the cap, so the open question is only how the check itself is written and tested, not
  whether it can fire in practice for this screen.
- [ ] **What does the screen show before any plan has ever been authored?** Not the same as "no
  planned day selected for today" (REQ-FR-260003 already covers that) — the true first-run case,
  before EPIC-260004 has produced a single plan. Named here because nothing in the current
  governance set owns it; it is not solved by treating it as a variant of the no-selection case,
  since there is nothing to select from.
