> **Plan amendment 2026-09-21, on the owner's instruction, before any code was written.** Once the owner
> supplied the real programme (`program-context.md`), which alternates A and B days across sessions, the
> owner replaced "today by weekday" with paging through every planned day, added reps counted per side and
> a cue line per exercise, and kept the day plans in `content/plan.json` with the Markdown holding the
> rationale. The epic stays `Ready` on that instruction; the bullets and tasks below are the amended plan,
> and [ADR-260008](../adr/ADR-260008.md) carries the matching amendment. The title changed from "Today's
> workout page from content files".

- Epic ID: EPIC-260007
- Title: Workout days page from content files
- Persona/Actor: The owner at the gym, phone in one hand, wanting to see the day's workout without
  signing in.
- Value statement: For the owner at the gym, deliver a page that shows each planned workout day —
  every exercise with two pictures of how to do it, its cue, its sets and its reps — so the programme
  is on the phone from the first release, before sign-in or the backend exist.
- Context: The owner's direction (2026-09-21): start with "something really simple" — a web page fed
  from content stored in files — with sign-in and the Crystord backend to follow. The programme is in
  `program-context.md`: three sessions a week, alternating A and B days, with Days 1–3 written out.
  The six earlier epics are parked (`epic-index.md`). This is the first code in the repository, so it
  is also the first build, the first test suite and the first deploy.
- Problem statement: Nothing is built. Every earlier epic depends on the backend, so none of them
  puts a workout on a phone soon.
- Expected outcome: opening the Pages URL on a phone shows Day 1 — its name and its exercises in
  order, each with two pictures, a cue, the number of sets and the reps per set — and the owner pages
  to any other planned day. Adding a day to the content adds a page; changing the content is a commit,
  and the deploy workflow republishes the site.
- Success metric(s): every day in `plan.json` is reachable on the deployed site; a content commit
  reaches the site with no manual step, and the footer shows its commit; a commit whose content fails
  a check is not deployed; at 360 × 640, sets and reps render at ≥ 24 CSS px, all other text at
  ≥ 16 CSS px, and the paging buttons are at least 48 × 48 CSS px (REQ-QR-260001); the initial
  payload stays ≤ 250 KB compressed and each picture within the budget below (REQ-QR-260002).
- Non-goals: sign-in; the backend; logging performed sets or weights; deciding which day is today;
  editing the plan in the app (it is edited in the files); showing the exercise pools, slots or
  rules from `program-context.md`; offline support; analytics.
- Constraints: GitHub Pages, static and public (REQ-OR-260001), so the plan and the pictures are
  world-readable; the stack of ADR-260007; the content model of ADR-260008; the page says "sets",
  not "sequences" (ADR-260001); one-thumb use at 360 × 640 (REQ-QR-260001); a slow gym connection —
  1.6 Mbps, 150 ms (REQ-QR-260002).
- Dependencies: the owner creates the GitHub repository and sets Pages → Source to "GitHub Actions"
  before the first deploy; the owner supplies the pictures, with placeholders until then.
- Risks/assumptions: assumes pictures arrive as full-size phone photos and must be resized to fit
  the budget; a base-path mistake shows up only on the first deploy, as a blank page; with many
  days, paging from Day 1 gets long — revisit if it does. Found in review (2026-09-21): on the
  reference phone, native lazy loading defers few of a day's pictures, so the cold-open budget must
  be measured on the live site once real photos exist; and above 200% browser text size on narrow
  screens the pager's "Next day" label runs off-screen (up to 200% is handled and tested).
- Target window: TBD.
- Validation approach: an end-to-end check on the built site, served under a sub-path — every day
  reachable, a reload keeps the day, and a measurement of text and button sizes at 360 × 640; the
  content check with negative controls in CI; unit and component checks on the pager and the day
  view.

## Ideation Bullets

Resolved in session on 2026-09-21. Bullets marked *Owner* were decided by the owner; the rest were
proposed and approved by the owner at the plan review ("I approve everything"), then amended on the
owner's instruction where the amendment note above says.

- [x] *Owner* — **Stack.** Vite + React + TypeScript, as in `crystord_app` — ADR-260007.
- [x] *Owner* — **Which day is shown.** Every planned day, one per page, in file order; more days in
  the content means more pages. The page does not decide which day is today.
- [x] *Owner* — **Where the data comes from.** Files in the repository, "for now used for content
  only"; the backend replaces them later. Day plans live in `content/plan.json`;
  `program-context.md` keeps the rationale, and its section 10 points to the JSON.
- [x] *Owner* — **What each exercise shows.** Two pictures, the cue line, sets, and reps — with
  "per leg", "per arm" or "per side" where the programme counts each side.
- [x] **Content format and its checks** — ADR-260008: two JSON files that mirror ADR-260001's
  vocabulary, readable slugs as keys, exactly two pictures per exercise, bundled at build time and
  validated in CI.
- [x] **Picture budget: at most 100 KB each, with fixed dimensions, lazy-loaded after the first
  exercise.** At REQ-QR-260002's 1.6 Mbps (≈ 200 KB/s) a 100 KB picture costs about 0.5 s, so the
  first exercise's two pictures fit the 4 s cold-open budget alongside the bundle; a 3 MB phone
  photo would cost 15 s on its own. Real pictures are resized before they are committed.
- [x] **Base path: relative (`./`)**, so one build works as a project site
  (`<owner>.github.io/<repo>/`) or on a custom domain. The hosting-target question stays in
  EPIC-260002 and must be answered before sign-in, because it decides which sites share Liftrack's
  browser origin (ADR-260005) — it does not block this page.
- [x] **The day in the URL fragment, no router.** `#day-2` keeps the day across a reload or a phone
  restoring the tab; nothing else is routed, and an unknown fragment shows the first day.
- [x] **Build identifier in the footer** (short commit hash and build time). Pages keeps no access
  logs, so this is the only way to tell whether a content commit has reached the phone.
- [x] **Overlap with the parked epics.** This epic builds the scaffold and a reduced Pages pipeline
  (lint, type check, tests, build, deploy) — EPIC-260002's scaffold part, without its backend
  configuration — and a read-only precursor of EPIC-260005's screen. Everything else stays in those
  epics.
