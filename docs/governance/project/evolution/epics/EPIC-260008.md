# EPIC-260008: Free text in the workout prescription

- Epic ID: EPIC-260008
- Title: Free text in the workout prescription
- Persona/Actor: The owner — writing the content files away from the gym, and reading the page at the
  gym with the phone in one hand.
- Value statement: For the owner, deliver a way to write a prescription in words where sets × reps
  cannot say it, so that every exercise the programme calls for can go on the page and none is shown
  as something it is not.
- Context: The owner's request (2026-09-24), after using the page [EPIC-260007](EPIC-260007.md) built:
  *"The format is too strict with the sets and reps. It should allow for just normal text as well,
  you know, underneath it."* Today a row of `content/plan.json` is an exercise, a set count (a
  positive integer), reps (a positive integer or a `{ "min", "max" }` range) and an optional `per`
  (`leg`, `arm` or `side`), and any other field fails CI ([ADR-260008](../adr/ADR-260008.md)'s
  Decision; `src/content-source/validate-plan.ts`, `raw-content.ts`). The only free text the content
  allows is an exercise's `cue`, which belongs to the catalogue entry and shows on every day that
  uses the exercise.
- Problem statement: parts of the owner's programme cannot be written in the format, so they are
  either left off the page or written as something they are not. Each case below was checked against
  the validator and the page:
  - a set range such as "2–3 sets" — `sets` must be one positive integer;
  - a timed hold such as a plank or a side plank — `reps` is a count, and the page always renders it
    as reps, so a 30-second hold would read "3 sets × 30 reps";
  - a carry measured in distance or time, such as a suitcase carry — the same;
  - an exercise done on one side only — `per` means "counted on each side", and no value means one
    side only;
  - reps that differ from set to set (12/10/8) — one count or one range covers every set, the limit
    ADR-260008's Consequences already name.

  Interim workarounds in `content/` since 2026-09-29, on the owner's choice when the full 40-workout
  rotation went into `plan.json` — to be undone when this epic lands: plank and side plank are
  written as seconds counted as reps (3×30, 3×20 per side), their cues opening "Reps are seconds
  held"; the shoulder-health slot's "2–3 sets" is written as 3.
- Expected outcome: every row the programme calls for can be written in `content/` and reads
  correctly on the page, and content that is broken still fails CI rather than reaching the site.
- Success metric(s): each case above can be written and is shown for what it is — no hold, carry or
  one-side row reads as ordinary reps; a misspelt field still fails the content check; any text on
  the card renders at ≥ 16 CSS px at 360 × 640 (REQ-QR-260001).
- Non-goals: the backend and its row shape ([EPIC-260001](EPIC-260001.md) carries that); editing the
  plan in the app ([EPIC-260004](EPIC-260004.md)); logging performed sets.
- Constraints: the content format and checks of ADR-260008, which a change here amends; the
  repository and the site are public — every committed line and its history is readable by anyone
  (README, "The repository is public too"); one-thumb reading at 360 × 640 (REQ-QR-260001).
- Dependencies: EPIC-260007's page and content format, whose tasks still await the owner's code
  review; the owner's acceptance of an ADR-260008 amendment before this epic can be `Ready`.
- Risks/assumptions: text escapes every check the numbers get — "3 × 10" mistyped in words is not
  caught, and a backend can later neither validate nor query it — so each row written as text trades
  a little of ADR-260008's "broken content cannot reach the site" for flexibility. A free-text line
  is the easiest place for a private detail to enter a public file, and a later edit does not remove
  it from history; this assumes notes are written as generic instructions only. Long text on a
  360-px card pushes the pictures and the next exercise down.
- Target window: TBD.
- Validation approach: the content check in CI, with a negative control for each defect the amended
  format defines; unit checks on how a prescription is described; an end-to-end check that a row
  with text shows it, at the required size, at 360 × 640.

## Ideation Bullets

Open questions from the owner's request, not yet discussed. None is resolved; no design is decided.

- [ ] **Underneath, or instead of?** Free text *underneath* the structured sets × reps — an optional
  line shown under the prescription, which is what the owner's "underneath it" describes — or free
  text *instead of* sets × reps for some rows, such as a hold, a carry or "2–3 sets". Underneath
  keeps every row's numbers but still shows a hold as reps; instead-of says the hold correctly but
  leaves that row with no numbers. The two can also coexist.
- [ ] **Does the page keep validating structured values?** Whether `sets` and `reps` stay required
  and checked on every row, become optional where text is given, or grow structured forms of their
  own — a set range, a duration, a distance, a one-side value — which would cover some of the cases
  above without text.
- [ ] **What does the CI content check enforce on free text?** Non-empty after trimming, as the
  day's `name` and the exercise's `cue` already are? A maximum length, so the card stays readable at
  360 × 640? One line or several? And, if text can replace the numbers, whether a row with neither
  still fails.
- [ ] **Row text or exercise cue?** The catalogue's `cue` is already free text, per exercise and
  shown on every day. Whether the owner's text belongs to the row (this day only), to the exercise,
  or to both — and where it sits on the card relative to the cue.
- [ ] **How does it map to the backend later?** `planday/v1`
  ([`liftrack-atom-shape-contract.md`](../contracts/liftrack-atom-shape-contract.md) §3.1) is
  `[ref, sets, repsMin, repsMax]`, integers after the reference cell, with no text column; the
  planned-day atom's `description` ("notes") is per day, not per row. Like `per` (ADR-260008's
  Risks), a text column has no place in `planday/v1`; moving it to the backend is a `planday/v2`
  amendment of the contract, raised when EPIC-260001 resumes, and `project-instructions.md` §6 asks
  for its ICR before it is written. EPIC-260004 settled a prescription's precision with free text
  considered and left out of the baseline row shape; this epic reopens that for the files, and its
  answer becomes the input to the amendment.
- [ ] **ADR-260008 amendment.** Accepting text needs an amendment of ADR-260008: its Decision defines
  the row's fields and fails CI on "any field the format does not define", and its Consequences name
  per-set reps as a limit the format keeps. The owner accepts or rejects that amendment at this
  epic's plan review.
