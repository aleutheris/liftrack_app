## Context

A plan says which exercises to do on a gym day and how many sets and reps; the user then records what was performed. Crystord Engine is the only
durable store. **Terminology, stated once for the whole project:** the owner's word *sequence* is the standard gym term **set** — a group of reps
performed consecutively without rest. Liftrack says **set** everywhere, and "sequence" in the interface would be a presentation choice. A **session**
holds **performed exercises**, each holding **sets** of **reps** at a **weight**.

Three verified engine facts decide the grain. (1) `retrieve` caps at 25 atoms, unraisable and unsignalled: the constants are `_DEFAULT_RETRIEVE_LIMIT
= 25` / `_MAX_RETRIEVE_LIMIT = 100` (`inter_fundamentals.py:1406-1407`), applied at `:1419`, with no limit forwarded (`resolvers.py:86-91`) and none
published (`schema.graphql:9`) — and it keeps the newest 25, dropping the oldest (`qt_fundamentals.py:708-709`). (2) `AtomOutput`
(`schema.graphql:249-263`) carries no timestamp, so a session is not findable by date. (3) Typed nested lists are shipped and tested (engine
REQ-FR-260009, ADR-260040) and `content` takes a string, number, array or null, never a bare object, so the only structured form is a positional
array. A session of 5-7 exercises x 3-5 sets is 15-35 atoms at set grain, 5-7 at exercise grain, 1 at session grain — against a page of 25.

## Decision

**One atom per performed exercise with its sets in a typed two-dimensional list; one atom per session; the plan as atoms down to the planned-day
level.** Field-by-field shape: the `liftrack-atom-shape` contract.

- Labels are a closed compiled-in `Lift`-prefixed vocabulary — `LiftExercise`, `LiftPlan`, `LiftPlanDay`, `LiftSession`, `LiftPerf`, plus opaque keys
  `LiftD20260912` (date), `LiftM202609` (month, sessions only), `LiftEx0007` (exercise), `LiftP0001` (plan); the charset
  `[A-Za-z_][A-Za-z0-9_]{0,127}` forces that date spelling. Multi-label `retrieve` is an AND intersection, making a day-scoped read one round trip of
  5-7 atoms; keys are never renamed, since renaming rewrites every atom carrying the label.
- Sets live in `content` as `declaredType: "list"`, `typeMode: "flexible"`, one all-numeric row per set — `[setIndex, reps, weight]`; unit, column
  order and a row-schema version live in `constants`. The **workout date is Liftrack's own data** (`LiftD…` and `constants.date`), never a backend
  timestamp. `operation`, `COLLECT`, workspaces and sharing are out of MVP scope.

A logged set on the wire, as `change(selector: $selector, inputs: $inputs, remark: $remark)` — `labels` resent whole (non-null on update too); `bonds`, `categories` and `constants` omitted, since present replaces and omitted keeps:

```json
{ "selector": { "uuid": "9c0d1e2f-3a4b-4c5d-8e6f-7a8b9c0d1e2f" }, "remark": "Liftrack: set 3 — 6 reps at 85", "inputs": [ {
  "labels": ["LiftPerf", "LiftD20260912", "LiftEx0007"], "properties": { "nuclearies": { "declaredType": "list",
  "typeMode": "flexible", "content": [[1, 8, 80], [2, 8, 80], [3, 6, 85]] } } } ] }
```

### The removable seam

`LiftM202609` is the one part of this design built to be deleted: it exists only so "show me September" is a single bounded read while no temporal
filter exists, and it is written at create, read by one query path, referenced by nothing else. Engine ICR-260024 — `Open`, drafted, **not approved**
— would replace it with a half-open `created: { from, to }` range, after which deleting it is a client-side edit and no migration. It removes neither
`LiftD20260912` (record time is not event time — a workout logged next morning was performed the day before) nor the 25/100 bounds.

## Alternatives Considered

- Option A — **one atom per performed set**: addressable sets, pure creates, no lost-update window, and a future offline queue would replay trivially.
  Rejected on arithmetic: 6 exercises x 4 sets plus the session is exactly 25 and 7 x 5 is 36, so eleven rows drop oldest-first and today's workout
  opens roughly a third of the way in. It buys no query power either, since `retrieve` filters by uuid, labels and categories only.
- Option B — **one atom per session holding everything**: wins the budget outright — 1 atom per visit, ~156 a year, eight weeks complete with every
  set in one 25-row read. Rejected on query-ability: nothing looks inside list content (engine ADR-260034 CT-12), one category value per dimension per
  atom, no full-text search — so "what did I bench last time" scans 25 sessions and answers "never" for a lift on a long rotation.
- Option C — **the plan as one document atom** instead of `LiftPlan` + `LiftPlanDay`: never capped, but a prescription row has no
  uuid, so "did I follow the plan?" is unanswerable. Adopt it if plan-versus-actual comparison is unwanted.

## Consequences

- Positive: today's plan and today's session are each one round trip of 5-7 atoms against a page of 25, and per-exercise history one round trip of the newest 25 performances; the first reachable truncation is at session 26, while browsing.
- Negative: a set is not individually addressable, so per-set annotations become extra numeric columns behind a `constants.schema` bump, and every aggregate is a client-side scan.
- Risks: the positional row contract is invisible to the server and can never be migrated by it — mitigated by versioning it in `constants.schema`.
  `declaredType`/`typeMode` are shipped but thinly documented, so the strings sent must be probed live first.

## Verification

- Contract check with a negative control: a session of 7 exercises makes `retrieve(labels: ["LiftPerf", "LiftD20260912"])` return exactly 7, while 26 atoms under one label return 25 with no error and no signal.
- Contract check: `content: [[1, 8, 80]]` reads back as nested numbers, never a string; a bare-uuid cell is rejected `AU-TYPE-MISMATCH` on create and `AU-TYPE-CONFLICT` on update.
- End-to-end: log five sets, reload, and assert the fifth set and the full label set both survive.

## Rollback

Changing grain is a data migration, not a config change: page every atom by label, write the new shape with batched creates, then
`destroy(selector: {uuids: […]})` the old ones. The cheap partial rollbacks are Option C and dropping `LiftM202609`; and until this ADR is accepted there is no data to migrate.
