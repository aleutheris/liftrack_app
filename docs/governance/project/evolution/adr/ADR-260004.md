# ADR-260004: Backend schema-compatibility handshake and version pinning

## Workflow

- Drafted 2026-09-12 from the vendored 9.3.0 contract, the sibling schema-compatibility contract and engine ICR-260024's consumer table, read as
  evidence. Nothing here is agreed; lifecycle per `artifact-model.md`.

Status: Proposed
Date: 2026-09-12
Owners: Repository owner

## Context

Liftrack consumes one live GraphQL schema, discovered at runtime through `schemaInfo` (`schemaVersion`, `schemaHash`, `releasedAt`). The backend's
compatibility contract makes `schemaVersion` authoritative, `schemaHash` diagnostic only, MINOR a backward-compatible addition and MAJOR the breaking
bump. A version gate buys one thing: it turns undefined behaviour — scattered nulls, a workout screen silently showing no sets — into one legible
refusal at one known point.

The failure mode is live. Engine ICR-260024 (`Open`, drafted, **not approved**) would move the schema `9.3.0` → `9.4.0` as a purely additive MINOR,
and its §3 consumer table records `crystord_app` across all three profiles and `crystord_gsheets` pinned `~9.3.0` = `>=9.3.0 <9.4.0` — **hard block**
on a change that cannot break them. Pages amplifies it: the add-on's block clears inside a 300-second cache, while a static bundle has no TTL and no
on-call. Only a commit heals it, and the owner is at the gym.

## Decision

- **Pin `^9.3.0`, not `~9.3.0`.** `^` trusts the compatibility policy the backend publishes; `~` distrusts it and pays with a certain outage on every
  additive release. If MINOR turns out not to be backward-compatible in practice, that is a defect to file against the contract, not a reason to
  pre-block every consumer.
- **Run `schemaInfo` network-only before any other operation** and gate boot on it; no query or mutation is issued first.
- **Four outcomes, four states, four user actions** — never one red screen. In range: boot. Below range: block, "the backend is older than this app".
  Above the major: block, "this app needs updating". `schemaInfo` unreachable: a connectivity state with retry, explicitly not an incompatibility
  claim. Unparseable version: block, naming the value received.
- **Diagnostics render in the UI, not only the console**: `schemaVersion`, `schemaHash`, build identifier and endpoint host. On a phone the console is
  unreachable, so a screenshot is the only diagnostic channel that exists.
- **A deploy-time gate probes the target deployment's `schemaInfo`** and fails the deploy when the configured range does not admit the reported
  version — the check that would have caught three sibling environments pinned below a backend heading past them.
- **The supported range lives in the generated `config.json`**, so narrowing or widening it is a configuration edit and a redeploy, not a code change
  — deliberately, so the fastest remedy is also the smallest.
- **Liftrack asks to be listed as a named consumer** in the engine's ICR consumer-impact table before ICR-260024 is decided, via
  [ICR-260003](../icr/ICR-260003.md). A row there turns a surprise outage into a known deploy dependency.

## Alternatives Considered

- Option A — **`~9.3.0`, matching the siblings**: maximal caution, and it would catch a backend that breaks compatibility inside a MINOR. Rejected
  because the cost is certain and the benefit speculative, and a Pages bundle cannot recover without a commit.
- Option B — **`>=9.3.0` with no upper bound**: never blocks, always boots. Rejected — a MAJOR release lands as missing fields at render time, the
  undefined behaviour the handshake exists to prevent.
- Option C — **no handshake at all**: one less request at boot. Rejected: the compatibility contract requires the check, and without it the first
  symptom of a mismatch is wrong data on a workout screen.
- Option D — **pin `schemaHash` instead of the version**: exact, detects any change at all. Rejected because the contract makes the hash
  diagnostic-only and every additive release would flip it — Option A's failure mode, stricter.

## Consequences

- Positive: an additive backend release does not take Liftrack offline; a breaking one stops it at one known point naming both versions; and the
  remedy for a wrong verdict is a config edit.
- Negative: Liftrack will sometimes run against a backend newer than the schema it was built from, so an unused new field or a newly reachable error
  code can appear before Liftrack knows of it — ADR-260006 defines how that is absorbed.
- Risks: `^` is only as good as the backend's discipline about MINOR; a stale cached `config.json` can carry a stale range; and the deploy gate cannot
  run against a backend that is down at deploy time.

## Verification

- Contract check against a stubbed `schemaInfo`, each paired with the positive control of 9.3.0 booting: 9.4.0 boots; 9.2.0 blocks as "backend older";
  10.0.0 blocks as "app older"; `"9.3"` blocks as an invalid version naming the value; a transport failure yields the connectivity state, not either
  block.
- End-to-end: the blocked state renders `schemaVersion`, `schemaHash`, build identifier and endpoint host on screen, and no `retrieve` or `change` is
  issued before the verdict.
- Deploy gate: a build configured `^9.3.0` against a deployment reporting `11.0.0` fails the deploy; the same build against `9.3.0` passes.

## Rollback

Narrowing to `~9.3.0` is one value in `config.json` plus a redeploy — no code change, no data change. Widening again is the same edit. If the
four-state handling proves wrong, collapsing to a single block state is a change inside the startup-check module alone, because nothing else reads
`schemaVersion`.
