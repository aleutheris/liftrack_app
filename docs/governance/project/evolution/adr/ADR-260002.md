# ADR-260002: Static single-page frontend on GitHub Pages

## Workflow

- Drafted 2026-09-12 from the GitHub Pages platform constraints and the sibling frontend's deploy pipeline, read as evidence only. Nothing here is
  agreed; lifecycle per `artifact-model.md`.

Status: Proposed
Date: 2026-09-12
Owners: Repository owner

## Context

The owner's only stated hosting requirement is "I do not actually care [about the stack], as long as it can be used in github pages". **No stack
preference was expressed**, so the toolchain is justified by convention reuse with the sibling frontend `crystord_app` — same build model, same
config-profile shape, same schema handshake — not by preference. If that reuse stops holding, the choice is re-argued, not defended.

Pages serves bytes only: no request-time code, no proxy, no rewrite rules, no response headers of our own, no access logs, and a world-readable bundle
even from a private repository. So deep links have no server-side fallback, configuration cannot be a runtime variable, and a deployed bundle cannot
heal itself — only a new commit can.

## Decision

- **Purely static SPA deployed from a build artifact**, with Crystord Engine over HTTPS as the only backend. Anything needing a third participant —
  hiding a secret, proxying CORS, exchanging an OAuth code — is out of scope and becomes a request to the engine.
- **Hash routing** (`/#/plan/monday`): the server only ever sees the site root and always answers 200. Liftrack has no SEO or link-preview
  requirement, so this removes a whole class of configuration failure for a cosmetic cost.
- **Build-time configuration in a generated, untracked `config.json` fetched at boot**, holding the GraphQL endpoint and the supported schema range.
  Still build-time; it buys repointing without a rebuild, and a legible failure.
- **The deploy gate asserts the positive condition** — the configured endpoint matches `^https://` — and CI never falls back to a developer profile. A
  `localhost` blacklist is not enough: a LAN endpoint such as `http://crystord:5665/graphql` passes it and ships a bundle that is mixed-content
  blocked on arrival.
- **One bundle, content-hashed asset names, and a build identifier (commit SHA and build time) rendered in the UI.** A deploy deletes the previous
  build's files, so a lazily imported chunk can vanish under a running session; the build id is also the only way to answer "which build is this?"
  without access logs.
- **Hosting target stays open and must be answered before the first deploy** — project site (`/liftrack/`, base path load-bearing), user site, or
  custom domain. A custom domain is recommended: every Pages project under one account shares one browser origin, which is also the deciding input to
  ADR-260005.
- **Achievable hardening only**: a `<meta>` CSP restricting `connect-src` to the engine origin, no inline handlers, no `unsafe-eval`.
  `X-Frame-Options`, `frame-ancestors`, HSTS and cache tuning are unavailable, so framing protection is **accepted as absent** rather than written as
  an unsatisfiable control.

## Alternatives Considered

- Option A — **clean URLs via the `404.html` redirect trick**, as the sibling does: nicer shareable links, but the first response is a genuine HTTP
  404, there is a redirect flash, it is dead without JavaScript, and its `pathSegmentsToKeep` constant must track the base path exactly or loop.
  Reconsider only if shareable clean URLs are wanted.
- Option B — **inline the endpoint into the bundle at build time**: removes the extra request and the config/bundle cache skew, but every repoint
  needs a rebuild. Rejected because the backend is a moving target.
- Option C — **host where a runtime exists**: gives real headers, a proxy, server-side secrets and logs. Rejected — it contradicts the owner's only
  hosting constraint.

## Consequences

- Positive: nothing to operate; a deploy is one artifact upload; configuration is one small file; the build is identifiable in the UI.
- Negative: URLs carry a `#`; no access logs, so the site can be wholly down and emit nothing; no response-header hardening; the fragment is spent on
  routing.
- Risks: a wrong base path ships a blank page whose console error names nothing about the base; `config.json` and the bundle cache independently, so a
  stale config can pair with a fresh bundle; a new custom domain has a certificate window in which every backend call is mixed-content blocked while
  the deploy looks green.

## Verification

- Deploy gate, failing the build: the generated `config.json` endpoint matches `^https://` and CI resolved the deploy profile, not the local one. A
  profile pointing at `http://crystord:5665/graphql` must fail — the case a `localhost` blacklist passes.
- End-to-end on the deployed URL: load the root, navigate to a second view, reload the browser, assert the view renders — the deep-link case hash
  routing solves by construction.
- Build check: every emitted JS and CSS filename contains a content hash, and the build identifier shown in the UI equals the deployed commit SHA.
- Pre-release check recorded once per hosting target: `curl -sSI <endpoint>` returns a valid certificate over HTTPS and the site answers 200 at its
  base path.

## Rollback

Everything here reverses by configuration or one module: routing is a router module plus a base-path value, and adopting the `404.html` scheme adds
two static files and one constant; inlining the endpoint is a build-script change; moving hosting target is a `base` value, a `CNAME` file and a
re-registered Google origin. No data is written, so nothing must be migrated back.
