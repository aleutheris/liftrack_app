## Context

The owner's direction for the first slice: a page "which feeds from content which are stored in files for now", showing the workout — the
exercises, two pictures of how to do each, the number of sets and the reps per set. Sign-in and the Crystord backend come later. The owner
writes the programme in `program-context.md` (rationale, exercise pools, rules, and the first planned days) and edits the data files by hand.

Three facts constrain the shape. The accepted domain model ([ADR-260001](ADR-260001.md)) and its shape contract already define the vocabulary:
an exercise catalogue whose entries carry coaching cues, planned days whose rows are an exercise, a set count and a target rep count or range
(`planday/v1`, §3.1), and a plan that is an ordered list of planned days (`plan/v1`, §3.3). A Pages site is public, so everything in the
repository is world-readable. And the engine accepts a string, number, list or null as `content` (`backend-user-guide.md:424`) — it has no
file or binary type to hold an image.

## Decision

- **Content lives in `content/`, is bundled at build time, and is never fetched at runtime.** A content change is a commit, and the deploy
  workflow rebuilds. Two JSON files and a picture folder — `content/exercises.json`, the catalogue:

  ```json
  { "leg-press":             { "name": "Leg press", "cue": "Feet mid-platform, knees track over toes",
                               "pictures": ["leg-press-1.webp", "leg-press-2.webp"] },
    "bulgarian-split-squat": { "name": "Bulgarian split squat", "cue": "Dumbbells at sides. Start light.",
                               "pictures": ["bulgarian-split-squat-1.webp", "bulgarian-split-squat-2.webp"] } }
  ```

  and `content/plan.json`, the planned days in the order they are paged:

  ```json
  { "days": [
      { "id": "day-1", "name": "Day 1 — type A", "exercises": [
          { "exercise": "leg-press", "sets": 4, "reps": 10 } ] },
      { "id": "day-2", "name": "Day 2 — type B", "exercises": [
          { "exercise": "bulgarian-split-squat", "sets": 4, "reps": 10, "per": "leg" } ] } ] }
  ```

- **The shape mirrors ADR-260001; it is not a new model.** The plan is an ordered list of planned days (`plan/v1`). A day's rows are
  `planday/v1` in named form — exercise, sets, and reps as a single count or a `{ "min", "max" }` range — in authored order, plus an optional
  `per` (`leg`, `arm` or `side`) where the reps count each side separately. An exercise is `exercise/v1`'s display name, its coaching cue
  (`exercise/v1`'s `description`, optional), and **exactly two pictures**, in order.
- **Keys are readable slugs** (`leg-press`, `day-1`), because the owner writes them by hand. Moving to the backend maps each exercise slug once
  to an opaque `LiftEx<NNNN>` key; the contract's opaque-key rule protects renames in the backend, which files do not need.
- **The page shows every planned day, one per page, in file order.** Adding a day to `plan.json` adds a page. The day being viewed is kept in
  the URL fragment (`#day-2`), so a reload — or a phone restoring the tab — stays on it; a fresh open, or a fragment naming no day, shows the
  first day. The page does not decide which day is today: the owner pages to it.
- **The page reads through one asynchronous interface** that answers "which days are planned" in domain terms. A file-backed source
  implements it now; the backend adapter implements the same interface later. The page renders loading and failed states from the start, so
  that swap does not restructure it.
- **Invalid content fails CI, so it never deploys**: no days at all; a day id that is not a slug or appears twice; a row naming an unknown
  exercise; a set or rep count that is not a positive integer, or a range whose `min` exceeds its `max`; a `per` other than `leg`, `arm` or
  `side`; an exercise without exactly two pictures; a missing picture file or one over the budget EPIC-260007 sets; and any field the format
  does not define, so a misspelt key is caught rather than ignored.
- **Pictures stay static files after the backend arrives.** The exercise record would then carry each picture's path, not the picture.

## Alternatives Considered

- Option A — **fetch the JSON at runtime from `public/`**: closer to a networked source, and editable without a rebuild. Rejected: on Pages every
  change is a commit and a rebuild anyway, and runtime JSON escapes the type check and the build-time validation.
- Option B — **YAML, Markdown front matter, or building from `program-context.md` itself**: friendlier to edit by hand. Rejected for now: it
  needs a parser, the Markdown tables would have to keep an exact format, and JSON is the shape the backend speaks. Revisit if editing JSON by
  hand proves painful.
- Option C — **a weekday map** (Monday → a day): the owner's first choice, accepted and then replaced the same day. It cannot follow an A/B
  alternation across sessions — every week would run A–B–A.
- Option D — **planned dates** (a date → a day): follows the alternation and skipped sessions, but the owner must list dates ahead of time.
  Not chosen; paging needs no dates at all.
- Option E — **opaque `LiftEx<NNNN>` keys in the files now**: a backend move with no mapping step. Rejected: a hand-written opaque key can be
  valid and wrong, and no check catches that.

## Consequences

- Positive: the owner maintains two small files and a folder of pictures; broken content cannot reach the site; the page order is `plan/v1`'s
  ordered list, so the move to the backend maps day for day; the backend replaces one implementation behind one interface.
- Negative: the plan and the pictures are public until sign-in exists. The page does not know which day is today — with many days, the owner
  pages further to reach it. A rep target that differs per set (12/10/8) cannot be written — the same limit as `planday/v1`.
- Risks: `per` has **no column in `planday/v1`**; moving it to the backend is a `planday/v2` amendment of `liftrack-atom-shape-contract.md`,
  raised when EPIC-260001 resumes. The page departs from REQ-FR-260003 (`Proposed`), which asks for the day's workout without the user
  choosing it.

## Verification

- The content check runs over the real `content/` in CI, with negative controls: a fixture carrying each listed defect must fail it.
- Unit checks on the pager: every day reachable in file order, the fragment read and written, and an unknown fragment falling back to the first
  day.
- End-to-end on the built site, served under a sub-path: every day in `plan.json` is reachable, each shows its exercises with sets, reps and
  both pictures, and a reload keeps the day being viewed.

## Rollback

Delete `content/` and the file-backed source; the page depends only on the interface. Nothing is written outside the repository, so nothing needs
migrating.
