## Context

The owner's only hosting constraint is GitHub Pages, and no stack had been chosen: `project-instructions.md` §7 carried a proposal pending
ADR-260002, which decides the delivery shape but names no framework. On 2026-09-21 the owner set the order of work — first a static page that
shows the day's workout from files in the repository, later sign-in and the Crystord backend — and parked the six earlier epics.

Two facts shape the choice. The page's one job, deciding which workout is today's, has to run **in the browser when the page opens**: a site
rendered at build time shows the build day's workout until the next deploy. And the same owner already maintains `crystord_app`, a Vite +
React + TypeScript client of the same backend, with Vitest, Testing Library, Playwright, ESLint and a GitHub Actions workflow that publishes to
Pages (read as evidence only). ADR-260002 had already justified Liftrack's toolchain by reuse with it.

## Decision

- **TypeScript (strict), React and Vite**, building to static files only. Nothing in the stack may assume a server (REQ-OR-260001).
- **Tooling matches `crystord_app`**: npm with a committed lockfile; Vitest with Testing Library (jsdom) for unit and component checks;
  Playwright for end-to-end checks against the built site; ESLint with `typescript-eslint` and the React hooks rules. Start on the majors
  `crystord_app` uses at the time of writing (Vite 8, React 19, TypeScript 6, Vitest 4) and move with it rather than drift.
- **Node 22 at build time only**, pinned in `.nvmrc`; CI reads the same file, so local and CI builds run one version.
- **Deploy by GitHub Actions to Pages** (`upload-pages-artifact` + `deploy-pages`), modelled on `crystord_app`'s workflow, running lint, type
  check and tests before the build, so a failing check never publishes.

## Alternatives Considered

- Option A — **plain HTML, CSS and JavaScript, no build**: fastest start, no dependencies. Rejected: nothing type-checks the content files, and
  sign-in plus a GraphQL client later means introducing a build and largely rewriting the page.
- Option B — **Astro**: made for content in files, ships little JavaScript. Rejected: it renders at build time, so "today" needs client code
  anyway, and the target app is a client-side SPA behind a sign-in.
- Option C — **Vite + Svelte + TypeScript**: a smaller bundle and less boilerplate on the same build model. Rejected: a second framework beside
  `crystord_app`, so no conventions or patterns carry over.

## Consequences

- Positive: one toolchain across the owner's two frontends; `crystord_app`'s sign-in, GraphQL-client and schema-handshake patterns carry over
  when the backend work resumes; the Pages workflow starts from one that already works.
- Negative: a build step and a framework runtime for what is today one screen; npm dependencies to keep current.
- Risks: React's runtime counts against REQ-QR-260002's 250 KB compressed initial-payload budget — small today, but measured from the build
  output, not assumed.

## Verification

- A fresh clone builds with `npm ci && npm run build` into static files only, with no server step.
- CI runs lint, type check, unit/component tests and the end-to-end check on every push to `main`, and any failure stops the deploy.
- The build's reported compressed bundle size stays under REQ-QR-260002's 250 KB.

## Rollback

While the app is one screen, replacing the framework rewrites only the view components: the content files and the source interface they sit
behind (ADR-260008) are plain JSON and TypeScript. Nothing is written anywhere, so there is no data to migrate.
