# ADR-260003: Online-only MVP without a local offline store

## Workflow

- Drafted 2026-09-12 recording the owner's settled MVP scope decision and its reasoning, so it is reversible on evidence rather than by argument.
  Nothing here is agreed; lifecycle per `artifact-model.md`.

Status: Proposed
Date: 2026-09-12
Owners: Repository owner

## Context

Liftrack is used standing at a rack, on a phone, on gym wifi or cellular, across a session that can run 45 minutes with long idle gaps — exactly the
pattern an offline store exists for. Choosing not to build one needs a stated reason and a stated way back.

The reason is cost, not impossibility. Three backend properties make a correct offline store materially harder than a cache: deletions are a hard
`DETACH DELETE` with no tombstone, so "what was removed while I was away" is unanswerable by construction; `content` is replace-whole with no partial
or append mutation, so merging two offline edits of one exercise atom is lossy by default; and `retrieve` returns at most 25 atoms with no truncation
signal, so a local mirror can never be proven complete. The contract also has no `Subscription` type, so there is nothing to listen to.

## Decision

- **MVP is online-only.** No offline store, no write queue, no background sync, no conflict handling. No workout data is written to `localStorage`,
  `sessionStorage` or IndexedDB — the only client-side persistence is the session token (ADR-260005).
- **Writes are per completed set**, one `change` against the performed-exercise atom, not one write at the end of the workout. The per-exercise grain
  (ADR-260001) makes this a single small mutation and bounds a connectivity loss to one set.
- **A set is shown as saved only when its mutation returns.** In flight and failed are distinct, visible states; a failed write keeps its typed values
  on screen with a retry. Silence is never rendered as success.
- **Freshness is user-triggered** — refetch on entering a view and on explicit refresh. No polling loop: there is nothing to reconcile, and a gym
  network is the wrong place to spend requests.
- **Re-authentication must not destroy in-progress input** (ADR-260005). With no queue behind it, an expiry between typing a weight and saving it is
  the one way a logged set can be lost.
- **Single-writer, single-device is an assumption, not a fact**, recorded as such: last-write-wins on whole-atom content is correct only while it
  holds.
- **What would change this decision** — three named observations, not opinions: the owner reports a gym where the app is unusable on the available
  signal; or a week of real use shows mutation failures at a rate the retry affordance does not absorb; or a second device or person starts writing,
  invalidating the assumption above. Any one reopens this ADR and pulls forward Option A.

## Alternatives Considered

- Option A — **full offline store with a write queue**: the honest answer to bad gym connectivity, and the per-exercise grain replays cleanly.
  Rejected for MVP on cost: it needs a merge rule for replace-whole content, a completeness story against the 25-cap, and an answer for deletions that
  leave no tombstone — three problems the product does not need solved to log a set.
- Option B — **read-only cache**, stale reads allowed and writes still online: cheap, and it makes today's plan visible on a dead network. Rejected
  because a cache that cannot also accept the log is half a feature carrying most of the invalidation cost.
- Option C — **a `localStorage` draft buffer** for the set being typed: the smallest useful step. Rejected because a draft outliving a reload still
  needs a reconcile rule against server state, and it puts workout data in an origin shared with every other Pages project on the account
  (ADR-260002).

## Consequences

- Positive: no cache invalidation, no merge semantics, no queue replay, and no stale read can be mistaken for truth; every screen shows what the
  server holds at that moment.
- Negative: with no signal the app is unusable rather than degraded, and a set typed during an outage is lost unless the user retries — at most one
  set, never a session.
- Risks: the single-writer assumption is unverified; and per-set writes turn a weak network into many small failures rather than one large one, which
  the retry affordance must make legible.

## Verification

- End-to-end with the network disabled mid-workout: the set being typed stays on screen, is marked unsaved, and is never reported as saved;
  re-enabling the network and retrying writes it once, with no duplicate atom.
- End-to-end with the network disabled at boot: the app shows a distinct connectivity state — not the schema-incompatibility state and not an empty
  plan (ADR-260004 defines the distinction).
- Architecture check: no production module writes workout data to `localStorage`, `sessionStorage` or IndexedDB; the only permitted key is the session
  token's.
- Contract check: one completed set produces exactly one `change` call carrying the whole `content` list, and the returned uuid matches the atom
  shown.

## Rollback

Reversing is additive, not destructive: Option A adds a store and a queue in front of the one module every mutation already passes through, and the
domain model does not change. The architecture check above is what keeps that true — if any module reaches the network directly, the seam is gone and
the rollback stops being cheap.
