# ADR-260005: Session token storage and re-authentication in a static browser client

## Workflow

- Drafted 2026-09-12 from the vendored 9.3.0 auth surface and the sibling frontend's re-auth detector, read as evidence. Nothing here is agreed;
  lifecycle per `artifact-model.md`.

Status: Proposed
Date: 2026-09-12
Owners: Repository owner

## Context

`signin` and `signinGoogle` return a bare session bearer token. It is not permanent: idle timeout about 24 hours, absolute cap about 30 days — both
approximate, so expiry cannot be computed client-side — and it is revoked by `logout`, `revokeAllSessions`, a password reset (all sessions, the
caller's included) and an email change (other sessions only). `setPassword` revokes nothing, and there is no refresh call or introspection, so any
request can discover the session is gone.

Liftrack has no server of its own (ADR-260002), so `HttpOnly` is unavailable. Two facts set the blast radius: a Pages origin is the host, not the
path, so every other project under the account shares Liftrack's storage; and the engine serves `Access-Control-Allow-Origin: *`, so a stolen token is
usable from any origin an attacker controls.

## Decision

- **Store the token in `sessionStorage` under a Liftrack-namespaced key.** It keeps what the user feels — a reload or deep link does not force a
  re-login mid-workout — while removing the indefinite at-rest token and the cross-project read `localStorage` would grant every other Pages project
  on the account. The cost, a re-login in a new tab, is near-zero for one user on one phone.
- **Seed the in-memory token synchronously at module import**, so the first request after a reload already carries `Authorization`
  rather than being answered as a re-auth.
- **`localStorage` is admissible only if the hosting target resolves to a custom domain** (ADR-260002), which removes the shared-origin blast radius.
  Recorded as a condition, not a promise; adopting it amends this ADR.
- **The token never appears in a log, URL, query string or routing fragment** — hash routing occupies the fragment, and a token there would land in
  browser history and in `Referer`.
- **Re-auth is detected on three signals**: HTTP 401, `extensions.code === 'UNAUTHENTICATED'`, and `AUTHZ-AUTHENTICATION-REQUIRED` inside the GraphQL
  error `message`, the form 9.3.0 actually emits. Matching a message substring is fragile by construction, so it is a named seam under ADR-260006,
  with "carry the code in `extensions.code`" as the durable fix to ask for.
- **On detection: discard the token, keep in-memory form state, re-authenticate over the current screen, and replay nothing.** Under ADR-260003 an
  unsaved set is unsaved; re-submitting it is the user's action, never a silent retry.
- **Whether to surface `revokeAllSessions` in the UI is left to EPIC-260003**, not decided here — the owner asked for a workout tracker, not an
  account-security surface, and this ADR should not pre-empt that epic's own open question on which account operations Liftrack exposes at all. What
  this ADR does settle: it is the only compromise-recovery lever a static client has, so if EPIC-260003 exposes any account operation beyond sign-out,
  this is the one with the strongest claim. A password reset ending the current session is presented as expected, not as an error, regardless.
- **Google sign-in is out of MVP scope until one prerequisite is granted.** The engine verifies a single server-configured client ID, so Liftrack
  cannot mint its own OAuth client: using Google means adding Liftrack's origin to the existing production client, an owner action. If adopted,
  `AUTH-GOOGLE-NOT-LINKED` must be actionable, because an unknown email silently creates a second, empty account.

## Alternatives Considered

- Option A — **memory only**: the smallest at-rest exposure, since an attacker must run while the app runs. Rejected alone, because every reload and
  deep link becomes a password prompt between sets; it is right only with a silent re-establish, which 9.3.0 does not offer.
- Option B — **`localStorage`, as the sibling does**: survives new tabs, and its synchronous seeding is well-reasoned. Rejected as the default: on a
  shared `github.io` origin it hands a 30-day bearer token to every other project on the account.
- Option C — **an `HttpOnly` cookie**: correct in general, unavailable here — it needs a server and a credentialed CORS posture the engine does not
  use.

## Consequences

- Positive: no token survives the tab; the exposure to a sibling Pages project is reduced to tabs Liftrack itself opened; expiry becomes a designed
  state rather than a generic error.
- Negative: a second tab requires signing in again, and a set typed just before an expiry must be re-entered.
- Risks: message-substring detection breaks silently if a code is renamed; `sessionStorage` still exposes the token to same-origin XSS while the tab
  is open; and the Google prerequisite, if found on deploy day, fails as `origin_mismatch` or `Invalid ID token`, neither naming the cause.

## Verification

- End-to-end: after sign-in a reload in the same tab stays signed in and the first request carries `Authorization`, while a new tab requires sign-in;
  positive control, a fresh sign-in reaches the plan view.
- Contract check with a stubbed error: HTTP 200 plus a `message` containing `AUTHZ-AUTHENTICATION-REQUIRED` and no `extensions.code` produces the
  re-auth state — the form the sibling's earlier detector missed. HTTP 401 and `UNAUTHENTICATED` do the same.
- End-to-end: forcing that error mid-set leaves the reps and weight on screen after re-auth, and the set writes once.
- Architecture and end-to-end check: across a full run no token value appears in `localStorage`, any URL, or console output; after `revokeAllSessions`
  the next request produces the re-auth state.

## Rollback

Storage sits behind one module with `read`, `write` and `clear`, so moving to memory-only or `localStorage` is a single-module change with no data
migration. If a token is believed leaked, `revokeAllSessions` invalidates it at once from any client that can call it — including outside Liftrack's
own UI, so nothing here depends on EPIC-260003 deciding to surface it.
