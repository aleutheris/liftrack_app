# ADR-260006: Capability-adaptive use of an evolving backend contract

## Workflow

- Drafted 2026-09-12 from the engine's own governance records (its epic index, ICR-260024 and the epics behind it), read as evidence. Nothing here is
  agreed.

Status: Proposed
Date: 2026-09-12
Owners: Repository owner

## Context

The owner's fifth standing input is that the backend is a moving target and Liftrack should challenge and influence how it stores and exposes
information rather than absorb its gaps silently. That makes "how do we behave while it moves" an architectural question.

The trajectory is visible but **not approved**. Engine ICR-260024 is `Open` — drafted 2026-09-08, and its §1 says approval has not been given — and
would add nullable `createdAt`/`updatedAt`, `created`/`updated` range inputs, a whitelisted `sort` and client-reachable `limit`/`offset` as an
additive MINOR `9.3.0` → `9.4.0`. Engine EPIC-260101 records that `retrieve` pagination is implemented and tested but unreachable, so no client can
see atom 26, and the deferred `100` → `500` raise sits behind engine EPIC-260099, in Ideation and unscheduled. The cap relaxes without vanishing, and
date filtering becomes native — later, if approved.

## Decision

- **Liftrack ships one code path at a time.** Adopting a backend capability is a release decision — raise the floor, delete the workaround, ship —
  never a runtime branch. No adapter per schema version, no layer keeping both shapes alive.
- **`schemaInfo.schemaVersion` is a boot gate, never a feature detector.** Only the startup check reads it (ADR-260004): no query builder, no view, no
  store. A version-keyed branch doubles the tested matrix, and the branch that runs at the gym is the one nobody exercised.
- **No runtime capability probing either** — a trial query costs a round trip at boot, can have side effects on atoms carrying an `operation`, and
  produces the same fork with worse diagnostics.
- **Every workaround lives behind exactly one named module and is registered here** with what it compensates for, the upstream change that deletes it,
  and the deletion cost. A workaround that cannot be removed by deleting one module is not accepted — it is redesigned until it can be.
- **The MVP register.** (1) The `LiftM202609` month-bucket label (ADR-260001), for the absent temporal filter; deleted by ICR-260024's `created`
  range; cost, a client-side edit and no migration. (2) The "a full page is presumptively truncated" heuristic, for the unsignalled 25-cap; superseded
  by overfetch-by-one once `limit` is reachable, then by a count surface ([ICR-260001](../icr/ICR-260001.md)); cost, one read module. (3) Matching
  error codes inside GraphQL `message` strings (ADR-260005); deleted if the engine moves them to `extensions.code`; cost, one error-mapping module.
- **One rule outlives every upstream change: never present a capped result as complete** ([REQ-CR-260003](../requirements/REQ-CR-260003.md)).
  ICR-260024 §2 states it is not a page-limit amendment and the raise past 100 is deferred, so bounded reads are a permanent property of this client.
- **Everything must be correct on 9.3.0 alone.** No record may treat ICR-260024 as a dependency; where one mentions it, it is marked as proposed upstream.
- **Adoption procedure when a version lands**: refresh the vendored `docs/backend/` copies, update the
  [crystord-graphql-contract.md](../contracts/crystord-graphql-contract.md) record, delete the named seam and its tests in one change, then raise the
  floor in configuration — never without a record.
- **Liftrack files consumer-backed requests rather than absorbing silently** — [ICR-260001](../icr/ICR-260001.md) and
  [ICR-260003](../icr/ICR-260003.md) — and asks for a row in the engine's consumer-impact table before a decision, not after. A third candidate,
  batch retrieval by UUID set, was considered and dropped: the atom shape (`liftrack-atom-shape-contract.md` §4) denormalises exercise name and
  prescription onto the atoms that need them, so rendering a screen resolves no bond references and the capability is not needed.
- **It also records what it will not ask for**, so the engine is not over-scoped on Liftrack's behalf: no domain event-time field, no append or
  partial-update mutation, no full-text search — each absorbed, with the reason in the record that absorbs it.

## Alternatives Considered

- Option A — **version-keyed adapters**, one query module per supported schema version: the conventional answer, and it would let Liftrack use
  `created` ranges the day they appear. Rejected — it multiplies the tested matrix by the number of live versions, and the failure it prevents is
  rarer than the one it creates.
- Option B — **runtime capability probing** at boot: more honest than a version number, since it tests the deployment itself. Rejected: it pays a
  round trip on the slowest network the app sees, and still ends in a fork.
- Option C — **wait for 9.4.0 before building the affected flows**: removes the workarounds entirely. Rejected — ICR-260024 is `Open` with no
  committed date, so the product would block on someone else's gate.
- Option D — **absorb every gap silently and file nothing**: cheapest short-term. Rejected against the owner's fifth input, and because the
  unsignalled cap is a correctness defect Liftrack cannot fix alone.

## Consequences

- Positive: one behaviour exists at a time, so what is tested is what runs; each workaround has a named module, trigger and deletion cost; the
  upstream backlog gains a documented consumer rather than a silent one.
- Negative: a capability cannot be used the moment a deployment gains it, since adoption waits for a release; and if the backend upgrades first,
  Liftrack keeps paying for a workaround it no longer needs.
- Risks: a seam can quietly become two, which the checks below exist to catch; and the register is only as good as its upkeep, so an unregistered workaround is a governance defect.

## Verification

- Architecture check: `schemaVersion` is read in exactly one module, the startup check; any other reference fails the check, which is what keeps the
  second decision true as the code grows.
- Architecture check: each register entry names exactly one module and that module is the only place its workaround appears. Positive control:
  deleting the module fails the corresponding tests and nothing else.
- Deletion rehearsal before the first release: a throwaway branch removing the month-bucket seam must touch only that module and its tests. Touching a
  view or a store means the seam is not isolated.
- Contract check: against a stub reporting `9.4.0`, Liftrack still issues the 9.3.0 query shapes and still boots, proving no query path reads the version.

## Rollback

The register is the rollback: re-adding a removed workaround restores one module and its tests, and lowering the supported floor is the configuration
edit ADR-260004 already defines. If the one-code-path rule proves untenable — say Liftrack must serve two deployments at different versions at once —
the way back is Option A, adopted by amending this ADR.
